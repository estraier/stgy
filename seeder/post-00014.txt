# STGYの主要クエリ分析

本記事では、STGYの運用上でデータベースに発行されるクエリについて分析する。SQLの具体例を示し、その計算量を解析し、実際の実行計画を見て確認する。

この精査で修正対象とするのは、元のSQLが意図した漸近計算量をSQLの形で保証していない箇所と、ページング結果を欠落させる箇所だけである。特定の検証データで実行時間やバッファ参照数を小さくするだけの書き換えは採用しない。

以下の実行計画は、``npm run reset-data-volume-test``で作成した検証用データベースを対象にする。``make-volume-test.py``は、既存の初期データに加えて、測定用ユーザ1人とダミーユーザ30000人を再現可能なIDと時刻で投入する。ユーザ活動は、投稿0件が12000人、1件が12000人、3件が4500人、10件が1350人、50件が150人というロングテールにする。さらに、長期利用する多投稿ユーザを模したuser00001のルート投稿20000件と、バズった投稿を模したuser00002から1番目のベンチマーク投稿への返信15000件を加え、測定用投稿は合計81502件になる。既存の初期投稿が15件の状態ではpostsの総件数は81517件になる。

フォロー関係も全員相互フォローにはせず、通常ユーザは人気アカウント4人と近接するユーザ8人を決定的にフォローする。測定用ユーザuser00000は5000人をフォローし、20000人からフォローされる高次数ユーザとする。これにより、多数の低次数ユーザ、数百から数千のフォロワーを持つ人気ユーザ、突出した高次数ユーザが同居する分布になる。1番目のベンチマーク投稿には20000件のイイネを付け、測定用ユーザは自分のフォロイーのうち投稿を持つユーザの最新投稿をイイネする。AIユーザはダミーユーザの5人に1人、計6000人とする。検索索引更新キューにはユーザタスク30000件と投稿タスク1000件を投入し、一方の種別が前方に偏って滞留した状態も再現する。イベントログ1000件と、測定用ユーザの未読15000件・既読15000件の通知も投入する。

最後にPostgreSQLの``ANALYZE``を実行するので、本記事のSQLはその直後に実行できる。スクリプトは、各比較で使うカーソルIDと実際の件数も表示する。測定用ユーザのIDは1853070350746583040で、ニックネームはuser00000である。短時間のOLTPクエリにJITコンパイル時間が混入する可能性がある測定では、セッションで``SET jit = off``を指定する。

## 最も単純な例
全ての投稿の中から最新20件を取り出す処理を考える。以下のクエリは実際には使われてないが、説明のための単純化したものを紹介する。デフォルトでは返信以外の投稿を一覧するため、reply_toがNULLであるという条件をつける。

```sql:small
SELECT
  p.id, p.owned_by, p.reply_to,
  p.allow_likes, p.allow_replies, p.updated_at
FROM posts p
WHERE p.reply_to IS NULL
ORDER BY p.id DESC OFFSET 0 LIMIT 20;
```

postsテーブルには、reply_toがNULLのレコードだけを対象としたIDの部分インデックスが設けられているため、そのインデックスを引くだけで処理が完了する。全ての投稿数をPと置くと、探索開始位置を求める計算量はO(log(P))で、そこから20件を読む部分は定数時間で済む。これは、Pが莫大になっても処理量が全件数に比例しないことを意味している。

現行のスキーマとデータで実行計画を確認するには、以下を実行する。実行時間や行数はデータ件数、統計情報、キャッシュ状態によって変わるため、実行後の出力を直後の結果欄へ記録する。

```sql:small
EXPLAIN (ANALYZE, BUFFERS)
SELECT
  p.id, p.owned_by, p.reply_to,
  p.allow_likes, p.allow_replies, p.updated_at
FROM posts p
WHERE p.reply_to IS NULL
ORDER BY p.id DESC OFFSET 0 LIMIT 20;
```


実測では``idx_posts_root_id``を逆方向へ走査し、20件を得た時点で停止した。追加のSortはなく、参照バッファは3ページ、実行時間は0.091msだった。返却件数が20件に固定されている限り、投稿総数に比例した走査は発生していない。

## listPosts
実運用上は、各投稿の著者のユーザIDを名前に解決したり、各投稿につけられたタグ情報やカウンタを結果に含めるために、別のテーブルをJOINすることになる。それを実装しているのが、バックエンドのpostsService.listPostsメソッドだ。reply_toがNULLで、focusUserIdを指定しない場合のクエリは以下のものになる。

```sql:small
SELECT
  p.id, p.owned_by, p.reply_to, p.published_at, p.updated_at,
  p.snippet, p.locale, p.allow_likes, p.allow_replies,
  id_to_timestamp(p.id) AS created_at,
  u.nickname AS owner_nickname,
  u.locale AS owner_locale,
  pp.owned_by AS reply_to_owner_id,
  pu.nickname AS reply_to_owner_nickname,
  COALESCE(pc.reply_count, 0) AS count_replies,
  COALESCE(pc.like_count, 0) AS count_likes,
  ARRAY(SELECT pt2.name FROM post_tags pt2
    WHERE pt2.post_id = p.id ORDER BY pt2.name) AS tags
FROM posts p
JOIN users u ON p.owned_by = u.id
LEFT JOIN posts pp ON p.reply_to = pp.id
LEFT JOIN users pu ON pp.owned_by = pu.id
LEFT JOIN post_counts pc ON pc.post_id = p.id
WHERE p.reply_to IS NULL
ORDER BY p.id DESC OFFSET 0 LIMIT 20;
```

最も単純な例と同様に、まず投稿IDの部分インデックスで返却対象を絞り、その20件に対してusers、posts、post_counts、post_tagsを参照して属性を肉付けする。focusUserIdが指定された場合には、投稿者がそのユーザをブロックしているかを判定する列も加わる。また、一覧を取得した後に、返却対象の投稿IDに限定して、そのユーザがイイネまたは返信をしているかを別の2クエリでまとめて調べる。

これの計算量を考えよう。全ユーザ数をUと置き、全投稿数をPと置く。まず、該当の投稿のリストを得るのに、インデックスが利けばO(log(P))+O(20)の計算量がかかる。20は定数なので、O(log(P))と表せる。そして、ヒットした20件の各々に対し、カウンタ、タグ、ユーザ名を解決する。各結合先で主キーや複合主キーのインデックスが利けば、20件は定数なので、全体の支配項はO(log(P))またはO(log(U))である。UはPよりも十分に少ないと仮定すると、全体の支配項はO(log(P))ということになる。

focusUserIdが指定された場合に、一覧取得後に実行するイイネ済み判定と返信済み判定の2クエリについても個別に実行計画を確認しておく。サービス層では、一覧で返す最大20件の投稿IDを配列として渡す。以下では、検証用データの既知の投稿IDを具体値として使う。

まず、イイネ済み判定は以下のクエリである。検証用データでは、user00001が1番目のベンチマーク投稿をイイネしている。

```sql:small
SELECT post_id
FROM post_likes
WHERE post_id = ANY(
  ARRAY[
    1855878856704991232,
    1855878856706039808
  ]::bigint[]
)
  AND liked_by = 1853160947712987136;
```

post_likesの主キーはpost_idとliked_byの複合キーであり、クエリの2条件と一致する。配列中の投稿IDは最大20件という定数なので、それぞれについて複合主キーを引ければ、投稿数やイイネ総数に比例せずに判定できる。現行の実行計画を確認するには、以下を実行する。


返信済み判定は以下のクエリである。検証用データでは、user00001が20000件の投稿を所有する一方で、user00002が1番目のベンチマーク投稿へ15000件返信する。以下の条件に一致する投稿は0件だが、reply_toだけ、またはowned_byだけで候補を得ると、reply_toだけなら15000件、owned_byだけなら20000件を候補として調べることになる。

```sql:small
SELECT reply_to

)
```

```sql:small
CREATE INDEX idx_posts_reply_to_owned_by
```

## listPostsByFollowees
STGYのSNSとしての典型的なビューは、「自分がフォローしているユーザの投稿の一覧」を見ることである。これがログイン直後のデフォルトのビューでもある。このクエリが効率的に処理できるかどうかがSNSの性能を決めると言って良い。

基本戦略としては、表示件数が20件という定数であることを利用して計算量の削減を図る。フロントエンドのデフォルトでは自分を含む最新アクティブユーザを最大20人選び、その各々から最新3件を取り出すことで、候補を最大60件に限定する。実際のクエリを具体値で表すと以下のようになる。返信を含める場合の例である。

```sql:small
WITH
all_followers AS (
  SELECT followee_id
  FROM user_follows
  WHERE follower_id = 1853070350746583040
  UNION
  SELECT 1853070350746583040
),
active_followers AS (
  SELECT af.followee_id AS owned_by, latest_post.id AS last_id
  FROM all_followers af
  JOIN LATERAL (
    SELECT p2.id
    FROM posts p2
    WHERE p2.owned_by = af.followee_id
```

- フォローしているユーザのIDと自分自身をall_followersというビューとして作る。フォローしているユーザのIDへ自分自身をUNIONで加えた集合を作る。
- all_followersの各ユーザについて、``(owned_by, id)``インデックスを末尾から引き、LIMIT 1で最新投稿だけを取得したactive_followersというビューを作る。

- candidatesの最大60件の投稿IDを並べ、最新20件に絞ったtop_postsというビューを作る。
- top_postsの各々のIDに対して、listPostsと同様に各種属性を肉付けする。

返信を表示しない場合には、active_followersとcandidatesの両方へ``p2.reply_to IS NULL``が加わる。APIでは一人あたりの取得件数をlimitPerUserで指定でき、フロントエンドのデフォルトが3である。focusUserIdが指定された場合のブロック判定と、取得後のイイネ・返信状態の追加もlistPostsと同じである。

以前のactive_followersは、対象フォロイーの投稿をまとめて読み、``DISTINCT ON (owned_by)``で各ユーザの最新投稿を選んでいた。そのSQLでは結合順と走査範囲をプランナに任せるため、選択されたフォロイーの投稿数が多いと、その投稿集合に比例して読む計画を取り得る。現行SQLはall_followersの各IDを外側に置き、``LIMIT 1``を持つLATERAL副問い合わせで索引検索を1回ずつ行うため、意図したフォロイー数Fに比例する計算量をSQLの形で保証する。

## listFriendsByNicknamePrefix

ユーザ名の入力補完では、自分、フォロー中のユーザ、その他のユーザの順に候補を返す。バックエンドのusersService.listFriendsByNicknamePrefixメソッドは、ページングに必要な件数をK=offset+limitとして、自分とフォロイーをpreferredへ集め、不足分だけをothersから補う。

フォロイーについては、ニックネームに一致する全ユーザからフォロー関係を確認するのではなく、user_followsからフォロイーを列挙し、各followee_idについてusersの主キーを引く。具体例は以下のクエリである。

```sql:small
WITH
self AS (
  SELECT 0 AS prio, u.id, lower(u.nickname) AS nkey
  FROM users u
  WHERE u.id = 1853070350746583040
    AND lower(u.nickname) LIKE 'user00%'
),
followees AS (
  SELECT 1 AS prio, fu.id, fu.nkey
  FROM user_follows f
  JOIN LATERAL (
    SELECT u.id, lower(u.nickname) AS nkey
    FROM users u
    WHERE u.id = f.followee_id
      AND u.id <> 1853070350746583040
      AND lower(u.nickname) LIKE 'user00%'
    LIMIT 1
  ) AS fu ON TRUE
  WHERE f.follower_id = 1853070350746583040
  ORDER BY fu.nkey USING ~<~, fu.id
  LIMIT 20
),
preferred AS MATERIALIZED (
  SELECT * FROM self
  UNION ALL
  SELECT * FROM followees
),
others AS (
  SELECT 3 AS prio, u.id, lower(u.nickname) AS nkey
  FROM users u
  WHERE u.id <> 1853070350746583040
    AND lower(u.nickname) LIKE 'user00%'
    AND NOT EXISTS (
      SELECT 1
      FROM user_follows f
      WHERE f.follower_id = 1853070350746583040
        AND f.followee_id = u.id
    )
  ORDER BY lower(u.nickname) USING ~<~, u.id
  LIMIT (
    SELECT GREATEST(0, 20 - COUNT(*))
    FROM preferred
  )
),
candidates AS (
  SELECT * FROM preferred
  UNION ALL
  SELECT * FROM others
),
page AS (
  SELECT id, prio, nkey
  FROM candidates
  ORDER BY prio, nkey USING ~<~, id
  OFFSET 0
  LIMIT 20
)
SELECT
  u.id, u.updated_at, u.snippet, u.nickname, u.avatar,
  u.ai_model, u.is_admin, u.block_strangers,
  id_to_timestamp(u.id) AS created_at,
  COALESCE(uc.follower_count, 0) AS count_followers,
  COALESCE(uc.followee_count, 0) AS count_followees,
  COALESCE(uc.post_count, 0) AS count_posts
FROM page p
JOIN users u ON u.id = p.id
LEFT JOIN user_counts uc ON uc.user_id = u.id
ORDER BY p.prio, p.nkey USING ~<~, u.id;
```

以前のfolloweesはuser_followsとusersの通常JOINだったため、プランナはフォロイー側からF人を調べる計画だけでなく、ニックネーム索引側から一致ユーザを読み、各候補のフォロー関係を確認する計画も選べた。後者は一致候補数をMとすると最悪O(M･log(F))で、MがUに近い場合には意図したO(F･log(U))にならない。LATERAL副問い合わせでfollowee_idごとの主キー検索を明示したのは、この結合方向を固定するためである。

自分の取得はusersの主キーでO(log(U))である。フォロイー数をFとすると、user_followsからF件を列挙し、その各々についてusersの主キーを引くので、followeesの支配項はO(F･log(U))である。ニックネーム前方一致の判定は主キーで取得した各フォロイー行に対して行う。Fに比例する処理は残るが、ニックネームに一致する全ユーザ数からフォロイーを探す方向にはしない。

preferredだけでK件に達しなかった場合に限り、othersを実行する。idx_users_nickname_idは``LOWER(nickname) text_pattern_ops, id``の複合インデックスである。``ORDER BY lower(nickname) USING ~<~, u.id``と書くことで、そのインデックス順に候補を読み、必要件数が揃った時点で停止できる。候補が自分またはフォロイーなら除外するため、実際に確認する候補数は検索語の選択度とフォロー関係の分布にも依存する。

## fetchBatch
通知を作成するワーカーがイベントログを読み出す際には、以下のようなクエリが実行される。

```sql:small
SELECT
  event_id, payload::json AS payload
FROM event_logs
WHERE partition_id = 0
  AND event_id > 1869468402083381248
ORDER BY event_id ASC
LIMIT 100;
```

主キーがpartition_idとevent_idの複合キーなので、そのインデックスを使えば効率的な実行計画になるはずだ。イベントログの件数をEとすると、探索開始位置を求める計算量はO(log(E))で、そこから最大100件を読む部分は定数時間で済む。partition_idを完全一致で指定しているため、ORDER BYにpartition_idを重ねて書く必要はない。

このクエリには落とし穴がある。event_id単体での検索性を確保するためにevent_idへB木のユニーク制約をつけると、そちらを使ってevent_idの対象範囲をスキャンしながら該当partition_idを拾う実行計画が選ばれる可能性がある。現行スキーマではevent_id単体の検索用にハッシュインデックスを使い、バッチ取得には複合主キーを使わせる。

## 現状の計算量上の懸念と対策状況

ここまでの個別クエリに加えて、コードベース全体を対象に、ユーザ数、投稿数、文書数、キュー滞留件数などの増加に対して処理量がどのように増えるかを確認した。ここで問題とするのは、単に実行時間や定数倍を短縮できるかではなく、元の用途に対して全件走査や二次時間が発生し、データ量の増加に伴って現実的に処理できなくなる経路である。

### AIユーザワーカーの全件巡回

AIユーザワーカーは、AIユーザを一定件数ずつ取得して全員を順番に処理する。従来は以下の形でOFFSETを増やしていた。

```sql:small
SELECT u.id, u.nickname, u.is_admin, u.ai_model
FROM users u
WHERE u.ai_model IS NOT NULL
ORDER BY u.id ASC
LIMIT 200 OFFSET 15000;
```

AIユーザ数をA、バッチサイズをBとすると、先頭から全件を巡回する間に読み飛ばす行数は``0 + B + 2B + ...``となる。そのため、索引探索を除いた行走査だけでも合計O(A² / B)になり、AIユーザが増えるほど一巡の処理量が二次的に増える。

これを、直前のバッチで最後に取得したIDをカーソルとして渡すキーセットページングへ変更した。

```sql:small
SELECT u.id, u.nickname, u.is_admin, u.ai_model
FROM users u
WHERE u.ai_model IS NOT NULL
  AND u.id > 1853160963440578560
ORDER BY u.id ASC
LIMIT 200;
```

``users``には``id WHERE ai_model IS NOT NULL``の部分インデックス``idx_users_ai_id``がある。各バッチはカーソル位置をB木から探して次のB件だけを読むので、全巡回で実際に通過するAIユーザ行はO(A)になる。バッチごとの探索を含めれば、全体は``O(A + (A / B)･log(A))``であり、従来の二次時間を避けられる。既存のOFFSETベースの一覧APIは互換性のため残し、AIユーザワーカーだけが``order=asc``と``after``を使う。

### 検索索引更新キュー

検索索引更新ワーカーは、投稿用とユーザ用のループを独立して動かし、各々について次のクエリで古いタスクから定数件を取得する。

```sql:small
SELECT id, name_prefix, doc_id, body_text, locale, doc_timestamp
FROM search_indexing_tasks
WHERE name_prefix = 'posts'
ORDER BY id ASC
LIMIT 100;
```

従来は``id``の主キーしかなかった。そのため、別の``name_prefix``のタスクがID順の前方に大量に滞留すると、目的のタスクを見つけるまで最大でキュー総数Qに比例する行を調べる可能性があった。特に、対象prefixのタスクが存在しない空振りポーリングも最悪O(Q)になる。

これを避けるため、以下の複合インデックスを追加した。

```sql:small
CREATE INDEX idx_search_indexing_tasks_name_prefix_id
ON search_indexing_tasks(name_prefix, id);
```

これにより、対象prefixの先頭へO(log(Q))で移動し、そこから最大B件だけをID順に取得できる。1回の取得は``O(log(Q) + B)``となり、別prefixのバックログ量には比例しない。

実測では両方とも``idx_posts_owned_by_id``をIndex Only Scanしたが、OFFSET版は10200件を通過し、42バッファ、2.745msを要した。キーセット版では``owned_by``と``id < ...``の両方が``Index Cond``に入り、200件だけを読み、3バッファ、0.318msで終了した。Heap Fetchesはいずれも0であり、全件エクスポートでバッチ位置に比例して増えていた読み飛ばしが解消されている。

### その他の懸念と現在の扱い

* 一般の一覧APIにはOFFSETページングが残る。深いページではoffsetに比例して読み飛ばすが、通常UIで何千ページも順にめくる用途は現実的ではなく、全件巡回するワーカーとは性質が異なる。``listUsers``と``listPosts``には後方互換性を保ったまま``after``を追加し、``order=asc``では``id > after``、``order=desc``では``id < after``によるキーセットページングも選べるようにした。従来のOFFSETは既存クライアントのため維持する。フロントエンドのユーザ一覧では、``listUsers``を使うAllタブとニックネーム条件付き一覧について、次ページを取得するための直前ページ最終IDをセッション内に保存して``after``を使う。訪問履歴のないページ番号をURLから直接開いた場合など、対応するカーソルがない場合は従来のOFFSETへフォールバックする。全文検索は``searchUsers``、FolloweesとFollowersは別APIを使うので、この``after``の対象ではない。``listUsers``のsocial順はIDだけではカーソルを表現できないので``after``の対象外とする。他の一般一覧APIについては現時点では保留する。
* PostgreSQLの``ILIKE '%...%'``による本文検索と正確な``COUNT(*)``は対象件数に比例する。ただし、現在はいずれも管理用途であり、公開の全文検索はTTTSへ分離しているため、現時点では保留する。
* ユーザ名の入力補完では、候補数が多い``listUsers``のsocial順検索を使わず、専用の``listFriendsByNicknamePrefix``を使っている。したがって、広いsocial前方一致検索は通常UIの入力補完経路には残っていない。
* ``listPostsByFollowees``、``BuildSearchSeedForUser``、``listFriendsByNicknamePrefix``のfollowees枝は、フォロイー数Fに比例する。これは全投稿または全ユーザを走査しないための現在の設計どおりであり、支配項はそれぞれO(F･log(P))またはO(F･log(U))である。Fが極端に増えた場合には、上限、重要フォロイーの事前選択、アクティブ集合や結果のキャッシュを検討する。
* focusUserIdのイイネ済み判定では、イイネ数が少ないユーザには``liked_by``側の索引、イイネ数が多いユーザには``(post_id, liked_by)``の複合主キーが選ばれた。後者では2条件がともに``Index Cond``へ入り、最大20件の候補投稿についてIndex Only Scanできることを確認した。データ分布に応じて適切な索引が選ばれているため、追加変更は行わない。
* TTTSの検索は新しい時系列シャードから順に調べ、必要件数が揃った時点で停止する。深さ上限、timeout、Redisキャッシュも設けており、最悪時に複数シャードを調べることは仕様として受け入れている。現時点では変更しない。

以上より、今回までに修正した計算量上の欠陥は、全AIユーザ巡回のOFFSET、検索索引更新キューの複合インデックス欠如、投稿エクスポートのOFFSETによる全件巡回の3件である。それ以外は、用途が限定された管理機能、通常UIだけで使う深いページング、または仕様として既知の線形性として整理し、実運用で問題が顕在化した時点で再検討する。

## 総評

ここまで見てきたように、通常の一覧表示で記事IDやユーザIDの候補を取得する処理では、できる限りインデックスを使って返却対象を先に絞るように、スキーマとクエリを設計している。各々のインデックスがメモリ上にキャッシュされる範囲では、高速なランダムアクセスが期待できる。ただし、本文に対する``ILIKE '%...%'``やフォロイー全員を調べる処理など、ヒット件数やフォロイー数に比例する経路も残っている。短いニックネーム前方一致のsocial順``listUsers``は入力補完では使わず、専用の``listFriendsByNicknamePrefix``へ置き換えている。公開の全文検索では外部検索サービスを使って、その負荷をPostgreSQLから分離している。

全体の最新投稿を一覧で使うlistPostsは、通常のIDやタグなどの条件ではインデックスから定数件を取得できる。全件エクスポートでは``after``と``idx_posts_owned_by_id``を使ってキーセットページングする。focusUserIdの返信済み判定はpostsのreply_toとowned_byの複合インデックスを使う。イイネ済み判定は、イイネ数が少ないユーザでは``liked_by``側の索引、イイネ数が多いユーザでは``post_likes``の複合主キーが選ばれ、後者では``post_id``と``liked_by``の両方が``Index Cond``に入ることを確認した。自分がフォローしているユーザの最新投稿を一覧で使うlistPostsByFolloweesと、AI検索シードを作るBuildSearchSeedForUserのactive_followeesは、どちらもフォロイー別に最新投稿を1件だけ索引検索するので支配項はO(F･log(P))である。イイネした投稿の一覧で使うlistPostsLikedByUserもliked_byとcreated_atのインデックスから定数件を取得できる。listFriendsByNicknamePrefixのfollowees枝はフォロイーF人を列挙して各ユーザを主キーで調べるため、支配項はO(F･log(U))である。preferredで不足する場合のothers枝は、ニックネーム索引を順序付きで走査し、ページングに必要な件数が揃った時点で停止する。ただし、ILIKEによる本文検索は全体件数に対して同じ保証を持たない。候補数が多いsocial順のlistUsersも同じ保証を持たないが、現在のユーザ名入力補完では使用していない。

listPostsByFolloweesとlistFriendsByNicknamePrefixのfollowees枝は、いずれもフォロイー数Fに比例して索引を引く。現行実装ではフォロイー数を200人などに制限する上限は設けていない。listFriendsByNicknamePrefixのothers枝は早期終了できるが、短い検索語に多数が一致し、その中の自分やフォロイーが多い場合には、必要件数より多くの候補を確認する可能性がある。利用規模が大きくなってこれらが問題になった場合には、上限、対象フォロイーの事前選択、結果のキャッシュなどを検討する必要がある。

UXの要求仕様でフォロイー数の制限ができない場合、毎回のクエリでフォローしている全員を対象にするのではなく、「重要フォロイー」のサブセットやアクティブユーザの集合を定期的に計算してキャッシュする方法が現実的である。ただし、キャッシュがなくても正しい結果を返せるDBクエリを基礎として持つべきである。

投稿記事の本文やユーザ自己紹介の本文などのでかいデータを取得する操作も、スケーラビリティの制限要因になる。主キーに紐づいたテーブル本体のレコードを読み出すという操作は、レコード数Nに対してO(log(N))の計算量に過ぎない。しかし、データの規模が大きいと遅くなる。メモリ上のキャッシュに乗り切らないので、毎回のアクセスでストレージにアクセスするからだ。HDDであればシークタイムも加算される。読み出しのデータが大きいと、ストレージとメモリの間のデータ転送量が増えることでも遅くなる。postsとusersテーブルに本文を入れずにスニペットだけを入れるのは、この問題に対する緩和策だ。計算量を対数オーダーにするのは大前提だが、計算量に現れない最適化も地味に性能に効いてくる。

* 限界点

個々のDBサーバが、いつどのように限界を迎えるのかについて考えておくべきだ。言い換えると、要求スループットに実際のスループットが耐えられなくなる瞬間は、いつ、どのように訪れるかだ。例えば100QPSを単一の直列実行で処理するなら、平均10ms以内で1件を処理し続ける必要がある。実際のPostgreSQLは複数接続で並列に処理できるため、許容レイテンシを単純に``1 / QPS``では決められない。CPU、ストレージ、ロック、接続数、クエリ同士のキャッシュ競合を含めた負荷試験で判断する必要がある。

リスト系クエリの処理が、インデックスを参照して返却対象のIDを絞り込むフェーズと、主テーブルを参照して個々のIDの属性を肉付けするフェーズから成ることは既に述べた。性能が低下する一つの契機は、頻繁に参照するインデックスとテーブルの作業集合が、PostgreSQLのshared_buffersとOSのページキャッシュに収まらなくなり、物理I/Oの割合が増えることである。shared_buffersを実メモリの25%程度から調整し始める構成は一般的だが、25%が常に最適という意味ではない。PostgreSQLのバッファとOSのページキャッシュの双方を考慮する必要があり、shared_buffersの容量だけが性能の境界になるわけでもない。

実際のテーブルやインデックスが占有しているデータサイズは、以下のクエリで確認できる。``pg_relation_size``を使うだけならpageinspect拡張は不要である。実運用を始めたら、定期的に結果を記録して増加率を確認すべきだ。

```sql:small
SELECT
  n.nspname AS schema,
  c.relname AS name,
  CASE c.relkind
    WHEN 'r' THEN 'table'
    WHEN 't' THEN 'toast'
    WHEN 'i' THEN 'index'
    WHEN 'm' THEN 'mview'
    ELSE c.relkind::text
  END AS type,
  pg_size_pretty(pg_relation_size(c.oid)) AS size_pretty,
  pg_relation_size(c.oid) / 8192 AS pages_8k
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND c.relkind IN ('r', 't', 'i', 'm')
ORDER BY pages_8k DESC;
```

投稿関係の7インデックスだけを取り出すには、以下を実行する。

```sql:small
SELECT
  c.relname AS name,
  pg_relation_size(c.oid) AS size,
  pg_relation_size(c.oid) / 8192 AS pages_8k
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind = 'i'
  AND c.relname IN (
    'posts_pkey',
    'idx_posts_owned_by_id',
    'idx_posts_reply_to_id',
    'idx_posts_reply_to_owned_by',
    'idx_posts_root_id',
    'idx_posts_root_owned_by_id',
    'idx_posts_public_owned_by_published_at'
  )
ORDER BY c.relname;
```

```:small
                  name                  |  size   | pages_8k
----------------------------------------+---------+----------
 idx_posts_owned_by_id                  | 2605056 |      318
 idx_posts_public_owned_by_published_at | 4472832 |      546
 idx_posts_reply_to_id                  | 2719744 |      332
 idx_posts_reply_to_owned_by            | 1245184 |      152
 idx_posts_root_id                      | 1777664 |      217
 idx_posts_root_owned_by_id             | 1998848 |      244
 posts_pkey                             | 1867776 |      228
```

7インデックスの合計は16687104バイトである。測定時の``posts``総件数81517件で割ると、このテストデータ分布では投稿1件あたり約204.7バイトになる。

仮に実メモリ16GiB、``shared_buffers`` 4GiBとし、その半分をインデックス、その80%を投稿関係のインデックスへ使えると仮定すると、投稿インデックスへ使える容量は約1.6GiBである。1.6GiBを約204.7バイトで割る単純な線形外挿では、約839万投稿分に相当する。

これは限界値ではなく、フェルミ推定級の目安に過ぎない。7インデックスは同じ行集合を対象にしておらず、データ分布、B木ページの充填率、更新と削除による膨張、VACUUMの状態によって投稿あたりの容量は変わる。実際のアクセスは新しい投稿に偏るため、全インデックスがキャッシュに入らなくても頻繁に使うページは残りやすい。OSのページキャッシュもある。一方で、listPostsByFolloweesのように多数のユーザについて索引をランダム参照するクエリは、作業集合が広がるほど物理I/Oの影響を受けやすい。

主テーブルのデータにも別のキャッシュ境界がある。postsとusersに本文を入れず、一覧に必要なスニペットと属性だけを置くのは、主テーブルの行とページを小さく保つためである。返却対象のIDを先に定数件へ絞り、その後にだけ主テーブルを参照する設計は、計算量だけでなくキャッシュ効率の点でも重要である。大規模なSequential Scanが頻発すると、他のホットページをキャッシュから追い出す可能性もある。

作業集合がメモリとOSキャッシュに収まらなくなると、性能はストレージのランダムI/O能力に強く左右される。HDDのランダムI/Oは一般に数百IOPS程度で、SSDやNVMeは桁違いに高いが、製品、RAID、クラウドの設定、同時実行数によって大きく変わる。何百万投稿の規模でどの程度のQPSが出るかは、現行スキーマと実運用に近いストレージで測定しなければ断言できない。容量からキャッシュ飽和の目安は計算できるが、実際のスケーラビリティの限界点はベンチマークテストを経て判断すべきである。
## 余談

スニペットをDBに保存するということは、「どう表示するか」というフロントエンド側のプレゼンテーションの知識をバックエンド側で持つことを意味するため、責任分割の観点では気持ち悪い。本文に関数従属しているスニペットを持つのは第3正規形の違反でもある。スニペットの形式や文字数制限を変えた際にDBのレコードを入れ直さなきゃならないのも嫌だ。しかし、その気持ち悪さを飲んでもやらねばならない。

投稿記事やユーザ自己紹介の本文を分離するという手法は、いわゆる垂直分割の一種である。属性データの特性に合わせて管理方法を分割する手法とも言える。本文だけDBサーバを分けてもいいし、列指向DBに入れてもいいし、S3に入れてクライアントに直接取得させたっていい。古い記事の本文は圧縮した上でアーカイブ用のストレージに入れてもいい。post_likesやuser_followsといったテーブルを別サーバで管理するのも良いだろう。

以上のことを鑑みると、リソースのリストを取得する処理は、常に二段構えで考えるべきだ。条件に該当するIDのリストを生成する段と、そのIDに紐づけて属性を収集する段だ。RDB1台運用だとその2段が一発のクエリでできるが、それでもサブクエリを使って敢えて2段に分けて書くのも良い考えだ。以下の二つのクエリは等価で、後者の方が若干遅いかもしれないが、いずれ垂直分割する際は、後者の書き方をしておく方がバグりにくい。

```sql:small
SELECT id, nickname, snippet
FROM users WHERE id > 0x0001000000000002
ORDER BY id LIMIT 10;

WITH cand_ids AS (
  SELECT id FROM users
  WHERE id > 0x0001000000000002
  ORDER BY id LIMIT 10
)
SELECT u.id, u.nickname, u.snippet
FROM users AS u
JOIN cand_ids AS c ON u.id = c.id
ORDER BY c.id;
```

ここで使った``0x0001000000000002``は、10進数では281474976710658に相当する。``0x``接頭辞による16進整数リテラルはPostgreSQL 16以降で利用できる。PostgreSQL 15以前で同じクエリを実行する場合は、10進数の281474976710658と書けばよい。

なお、PostgreSQLでは、TOAST（The Oversized-Attribute Storage Technique）という機構があり、大きい可変長データを暗黙的に圧縮したり別領域へ移動したりする。SELECT対象に含めない外部TOAST値まで毎回読み出されるわけではない。しかし、主テーブルにはTOASTポインタやインライン部分が残り、短い本文は行内に格納され得る。行が太いほど1ページに入るレコード数が減るため、一覧で常用するpostsやusersを小さく保つという目的では、本文を別テーブルへ分ける効果がある。参照頻度の異なるデータを明示的に分けることで、意図せず本文を取得するクエリも避けやすい。

![TOAST図解](/data/help-postgres-toast.png){grid,size=large}

列のストレージ方式は``PLAIN``、``MAIN``、``EXTERNAL``、``EXTENDED``で調整でき、圧縮方式も列単位で選べる。ただし、短い値を常に別領域へ追い出すという単純な指定ではなく、行サイズやTOAST閾値に基づいて格納方法が決まる。TOASTの主目的は、大きな可変長値を扱いながらヒープ行をページへ収めることである。今回は圧縮方式としてLZ4を使う設定にしており、圧縮率と展開速度のバランスを取っている。それでも、ホットな一覧用属性と大きな本文の参照頻度が明確に異なるなら、テーブルを分ける方が設計意図を表しやすい。

参照系のクエリが重い場合、マスター・スレーブのレプリケーションを導入すると簡単に負荷分散できる。DBサーバを2台立てて、更新系クエリはマスターサーバにだけ投げるようにする。その更新内容はスレーブサーバに自動的に伝搬する。参照系クエリはマスターとスレーブの双方に分散して投げると、参照系クエリの負荷はサーバあたりで半分になる。スレーブの数を増やせば参照系の負荷はもっと下げられる。マスターが死んだ時にスレーブをマスターに昇格させることで、可用性の向上にもなる。ただし、更新系クエリの負荷はこの方法では下げられない。また、マスターからスレーブに更新が伝搬するまでにタイムラグがあるので、スレーブからの結果をそのまま表示すると直前の更新操作が反映されない可能性がある。よって、更新操作直後の参照系クエリはマスターにだけ投げるとか、更新内容をキャッシュサーバに入れておいてUI上で注入するとか言った工夫が必要になる。

垂直分割やレプリケーションをしても処理しきれなくなってきたら、いよいよ水平分割をすることになる。ユーザIDを使ってパーティショニングを行うのが率直な方法だろう。ハッシュ値などで機械的に割り振っても良いが、各ユーザがどのパーティションに居るのかを管理するuser_partitionsテーブルを作るか、それに相当するKVSを運用するのが率直だ。usersテーブルを引く時はユーザIDでパーティションを特定してからそのDBサーバにアクセスし、postsテーブルを引く時は著者のユーザIDでパーティションを特定してからそのDBサーバにアクセスする。フォロー関係は、フォロー元のユーザとフォロー先のユーザのDBに二重化して持たせれば良い。垂直分割を経ているならば、もはやJOINするクエリは少なくなっていて、IDのリストを取り出してから別のDBにアクセスする作法は確立しているはずだ。あとはそのアクセス先を個々のIDに紐づいたパーティションにするだけだ。ユーザに紐づいた一連のデータをパーティション間で移動するユーティリティさえ書いておけば、運用はそんなに難しくない。

規模が大きくなると、投稿一覧の「All」のビューがほとんど意味をなさなくなってくる。見知らぬ人の投稿を全て見る奴は居ない。となると、「Pickup」とか「Topics」とかいう位置づけのビューを代わりに置くことになるだろう。最近の投稿だけを集めた小さいデータベースを作っておいて、質が高いものや個々のユーザの興味に近そうなものをバッチ処理で計算して、それを提示するのだ。

規模が大きくなると、「セレブユーザ」の存在が運用上の問題になってくる。数万人からフォローされるユーザが出てくるかもしれない。単一の投稿がものすごい勢いでイイネされたり返信されたりするかもしれない。参照系を最適化するだけでは、更新系が逼迫する問題には対処できない。その場合、セレブユーザ専用のデータ管理機構を整備すべきだろう。投稿の内容はキャッシュサーバから配信し、フォローやイイネや返信はキューに入れて非同期に処理する。通知は意味をなさないので処理を省略する。セレブユーザではなくても、突発的なバズりや炎上はあり得る。それに備えて、負荷が一定を超えたら、全体または特定ユーザを対象とする更新操作を非同期処理に切り替える機構を入れてもよいだろう。時間分散という考え方だ。非同期処理にすると更新結果がすぐに画面に反映されないという問題が起こるが、そこはキャッシュで頑張る。つまり、ユーザ毎の更新内容をキャッシュしておいて、あたかもその更新が既にDBに反映されているかのように、表示に細工をするのだ。

その他にも、キャッシュサーバでできることはたくさんある。例えば、listPostsByFolloweesの中で作っているアクティブユーザリストをキャッシュすると、それだけでDBへの負荷が激減する。各アクティブユーザの最新投稿20件の内容もキャッシュしておけば、多くの場合で、DBに全くアクセスしなくても、タイムライン表示が完結する。DB設計の話から逸脱するのでここでは詳述しないが、キャッシュ機構の設計も重要だ。ただし、キャッシュはいつだって消えるので、キャッシュがなくても満足に動くDB設計をするのが大前提だ。

ここまでいろいろ述べたが、STGYの現状の目標は、スケーラビリティを追求することではない。SNSの基本機能を率直に実装した、シンプルで典型的で教科書的なシステムを作ることだ。少なくとも開発の初期段階では、見通しがよく開発と保守がしやすいスキーマを選択すべきで、現状のスキーマはそれに叶うものになっている。時期尚早の最適化をして、人気が出る前に開発が頓挫するというのでは意味がないので、シンプルな構成から始めるというのも重要だ。
