# STGYの記事外部公開機能

本記事では、STGYの記事をログインしていない閲覧者へ外部公開する仕組みと、その公開記事のページビューを数えるアクセスカウンタについて説明する。外部公開ページは、SNS内部の投稿データを別のブログデータへ複製するのではなく、同じ投稿を公開日時で選別して、ブログ風のレイアウトで表示する。アクセスカウンタは、個々のアクセス履歴をPostgreSQLへ蓄積せず、Redis上の小さな日次カウンタと重複排除データだけで直近10日間を集計する。

SNS内部の記事画面は、投稿者、イイネ、返信、タグ、編集操作などを中心に設計される。一方で外部公開ページには、サイト名、記事タイトル、公開日時、前後記事、プロフィール、最近の記事、人気記事、OGPメタデータなどが必要になる。STGYでは、投稿の正本とMarkdown変換処理を共用しながら、内部画面と外部画面の取得APIと表示コンポーネントを分離している。

アクセスカウンタについても、一般的なアクセス解析サービスのように、時刻、URL、IPアドレス、User-Agent、参照元などを一件ずつ保存するものではない。必要なのは、公開サイトの所有者が直近の閲覧状況を把握し、公開ページのサイドバーへPopular entriesを出すことである。目的をそこへ限定し、保存量と集計量を小さくしている。

## 公開状態の正本

投稿の外部公開状態は、``posts.published_at`` だけで管理する。

```sql:small
CREATE TABLE posts (
  id BIGINT PRIMARY KEY,
  owned_by BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  reply_to BIGINT,
  published_at TIMESTAMPTZ,
  updated_at TIMESTAMPTZ,
  snippet VARCHAR(4096) NOT NULL,
  locale VARCHAR(50),
  allow_likes BOOLEAN NOT NULL,
  allow_replies BOOLEAN NOT NULL
);
```

``published_at`` がnullなら外部非公開である。値があっても、その時刻が未来なら予約公開の状態であり、外部公開APIはまだ返さない。現在時刻以前になった投稿だけが公開済みとして扱われる。

```text:small
published_at = NULL       → 非公開
published_at > 現在時刻   → 予約公開
published_at <= 現在時刻  → 公開中
```

投稿一覧のメニューにあるExternal publicationダイアログでは、Publish this postの有無と公開日時を設定する。公開を解除すると ``published_at`` をnullへ戻す。公開用の記事テーブルや静的HTMLファイルは作らないため、公開後に投稿本文を編集すれば、外部公開ページにも同じ内容が反映される。これは公開時点のスナップショットを保存する方式ではなく、SNS内の投稿を現在の内容で外部表示する方式である。

公開日時は投稿IDとは独立している。作成から時間が経った記事を新しい公開記事として出したり、複数の記事へ任意の公開順を設定したりできる。公開一覧と前後記事の順序は、``published_at`` と投稿IDの組で決める。同じ公開日時を持つ投稿があっても、投稿IDを第二キーにすることで順序が一意になる。

## 外部公開ページの構成

外部公開には、ユーザ単位のサイトページと、投稿単位の記事ページがある。

```text:small
/sites/{userId}  公開記事の一覧とサイト紹介
/pub/{postId}    一つの公開記事
```

サイトページは、公開済み投稿を公開日時順で取得する。Rich表示では投稿のJSONスニペットを記事風に描画し、Plain表示では公開日、タイトル、著者、説明を簡潔な一覧にする。新しい順と古い順を切り替えられ、RichとPlainではそれぞれ別のページサイズを設定できる。

記事ページは、Markdown本文を外部公開用のHTMLへ変換し、公開日時、前後記事、サイドバーを付ける。サイドバーには、設定に応じて次の要素を表示する。

- サイトのプロフィール
- 最近公開された記事
- 直近10日間のPopular entries

最近の記事とPopular entriesは最大20件に制限する。DBに保存された設定値自体は変更せず、取得および表示時に ``Config.PUB_SIDE_POSTS_MAX`` で丸める。設定ミスで非常に大きな件数が入っても、公開ページのDB問い合わせやHTML生成が無制限に増えないようにするためである。

公開ページのデザインは、通常の横書き、新聞風、ホワイトボード風、ダークテーマに加えて、縦書き系のテーマを選べる。Markdown本文そのものは共通だが、縦書きテーマではMarkdown変換時にwriting modeを渡して、文字方向に依存する表現を変換する。記事内の画像や経路地図は、サーバ側で基本HTMLを生成した後、ブラウザ上の専用コンポーネントで操作可能な表示へ仕上げる。

## 公開サイト設定

ユーザごとの外部公開設定は ``user_pub_configs`` に保存する。

```sql:small
CREATE TABLE user_pub_configs (
  user_id BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  site_name VARCHAR(50) NOT NULL DEFAULT '',
  subtitle VARCHAR(50) NOT NULL DEFAULT '',
  author VARCHAR(50) NOT NULL DEFAULT '',
  introduction VARCHAR(1000) NOT NULL DEFAULT '',
  design_theme VARCHAR(50) NOT NULL DEFAULT '',
  show_service_header BOOLEAN NOT NULL DEFAULT TRUE,
  show_site_name BOOLEAN NOT NULL DEFAULT TRUE,
  show_pagenation BOOLEAN NOT NULL DEFAULT TRUE,
  show_side_profile BOOLEAN NOT NULL DEFAULT TRUE,
  show_side_recent INTEGER NOT NULL DEFAULT 5,
  show_side_popular INTEGER NOT NULL DEFAULT 5
);
```

サイト名、サブタイトル、既定の著者名、紹介文、デザインテーマのほか、サービスヘッダ、サイト名、前後記事、プロフィールの表示を切り替えられる。最近の記事とPopular entriesはBooleanではなく件数で指定し、0以下なら非表示とする。

設定画面はPublicationsページのSettingsタブに置く。設定の読み出しは外部公開ページからも必要なので公開APIであるが、更新は本人または管理者だけに許可する。設定レコードがまだない場合は既定値を返すため、外部公開を始める前に設定行を明示的に作っておく必要はない。

## 公開記事を取得するAPI

通常の投稿APIは、ログインユーザとの関係、ブロック状態、イイネ状態、返信状態などを扱う。外部公開では認証なしで利用できる一方、未公開投稿を絶対に返してはならない。そのため、公開用の取得経路を明示的に分ける。

主なAPIは以下の通りである。

|*API*|*用途*|
| ``GET /posts/pub/{id}`` | 一つの公開記事と前後記事IDを取得する |
| ``GET /posts/pub-by-user/{userId}`` | ユーザの公開記事を公開日時順で取得する |
| ``POST /posts/pub-by-ids`` | 指定されたID順に公開記事を取得する |
| ``GET /users/{id}/pub-config`` | 公開サイト設定を取得する |
| ``GET /users/{id}/pub-ranking`` | Popular entries用のIDとPVを取得する |
| ``GET /users/{id}/pub-stats`` | 所有者向けの詳細統計を取得する |

``GET /posts/pub/{id}`` は、対象投稿に ``published_at <= 現在時刻`` を要求する。同じ所有者の公開済み投稿から、公開日時とIDを使って直前と直後の記事を一つずつ求める。

```sql:small
WHERE p.id = $1
  AND p.published_at <= $2
```

前後記事は概念的には次の条件で取得する。

```sql:small
(published_at, id) < (current_published_at, current_id)  -- older
(published_at, id) > (current_published_at, current_id)  -- newer
```

``GET /posts/pub-by-user/{userId}`` は、サイト一覧とRecent postsに使う。絞り込みと並び替えをPostgreSQLで完結させる。

```sql:small
WHERE p.owned_by = $1
  AND p.published_at <= $2
ORDER BY p.published_at DESC, p.id DESC
OFFSET $3
LIMIT $4
```

``POST /posts/pub-by-ids`` はPopular entriesに限らない汎用APIである。検索、推薦、ランキングなど、別の処理で決めた投稿ID配列から表示用投稿データを取得する用途に使える。内部では既存の ``PostsService.listPostsByIds`` を利用し、PostgreSQLの ``WITH ORDINALITY`` で入力順を維持する。

```sql:small
WITH req AS (
  SELECT id, ord
  FROM unnest($1::bigint[]) WITH ORDINALITY AS t(id, ord)
)
SELECT ...
FROM req r
JOIN posts p ON p.id = r.id
ORDER BY r.ord
```

APIは取得後に未公開投稿と未来公開投稿を除外し、入力は最大20件に制限する。Popular entries専用の投稿取得APIを作らず、ランキング処理はIDとPVだけを返し、投稿データの取得はこの汎用経路へ集約している。

```text:small
Redisで人気順のIDを取得
  ↓
[idA, idZ, idB]
  ↓ POST /posts/pub-by-ids
同じ順序の公開Post[]を取得
  ↓
Recent postsと同じスニペット描画
```

ランキングに残っている投稿が後から非公開になった場合や削除された場合は、``pub-by-ids`` の結果から自然に除外される。

## サーバサイドレンダリングとメタデータ

``/sites`` と ``/pub`` はNext.jsのサーバコンポーネントとして描画する。ブラウザでJavaScriptが起動してから本文を取得するのではなく、最初のHTTP応答に記事HTMLを含める。ログインを前提としない閲覧者や検索クローラにも、記事本文と基本ナビゲーションを返せる。

記事ページのメタデータは、Markdownから抽出したタイトル、説明、著者、日付、featured imageと、公開サイト設定を組み合わせて生成する。主な出力は次の通りである。

- HTML titleとdescription
- canonical URL
- Open Graph Protocolのtitle、description、site name、locale、公開日時、画像
- Twitter Card
- author
- Dublin Core系のtitleとdate

canonical URLは ``/pub/{postId}`` とする。SNS内部の ``/posts/{postId}`` とは表示目的が異なり、外部共有されるURLを一つに固定する。

Next.jsはページ本体とメタデータ生成の双方で同じ記事データを必要とする。STGYではReactの ``cache`` を使って、同一レンダリング中の公開記事取得を共有する。これにより、メタデータ生成とページ生成によってバックエンドの公開記事APIが二重に呼ばれ、同じアクセスが二重計上されることを避ける。

## アクセスカウンタの要件

アクセスカウンタは、直近10日間について以下を提供する。

- 公開サイト全体のPV合計
- 投稿別PV上位1000件
- 公開記事サイドバーのPopular entries

一方で、次の情報は保存しない。

- 個々のアクセス時刻
- 生のIPアドレス
- User-Agentの履歴
- 参照元URL
- 閲覧者ごとの行動履歴

アクセス履歴をPostgreSQLへ保存すると、公開ページを一回表示するたびに永続的なINSERTが発生する。履歴テーブルは閲覧数に比例して増え、保持期限、パーティション、削除、集計インデックスなどの運用が必要になる。STGYで必要なのは高機能なアクセス解析ではないため、Redis上の日次カウンタへ直接集約する。

Redisの統計はキャッシュに近い補助データであり、消失しても投稿の正本は失われない。Redisを初期化すればPVは0から再開する。この割り切りによって、バックアップ、移行、整合性維持の対象を増やさない。

## ボットの除外

検索エンジンやSNSのリンクプレビューが記事を取得するたびにPVを増やすと、人間による閲覧数と大きくずれる。そこで、公開ページを受け取ったFrontendは、User-Agentでボットを名乗っているクライアントを、Redisへ到達する前に除外する。

現在は、``bot``、``crawler``、``spider``、``slurp``、``facebookexternalhit``、``bingpreview`` などを判定する。ボットと判定した場合は、PV記録用ヘッダをBackendへ送らない。本文とOGPは通常どおり返すので、検索登録やリンクプレビュー自体は妨げない。

これは善意のボットを除く仕組みである。User-Agentを通常ブラウザへ偽装するクライアントを厳密に判別するものではない。アクセスカウンタの目的は課金や広告精算ではなく、サイト所有者が傾向を見ることなので、複雑なボット判定基盤は導入しない。

## IPアドレスのフィンガープリント化

同一の閲覧者がページを再読み込みするたびにPVを増やさないため、同一投稿と同一IPアドレスの組を重複排除する。ただし、生のIPアドレスはRedisへ保存しない。

Frontendは、リバースプロキシから渡された ``X-Forwarded-For``、``X-Real-IP``、``CF-Connecting-IP`` の順でクライアントIPを取得する。IPv4とIPv6を正規化した後、共有秘密を鍵とするHMAC-SHA256を計算し、先頭4バイトだけをフィンガープリントとして使う。

```text:small
client IP
  ↓ HMAC-SHA256(shared secret)
32 bytes
  ↓ 先頭4 bytes
32-bit fingerprint
```

鍵なしハッシュでは、IPv4の候補を総当たりして元のIPアドレスを推測できる。HMACにすることで、Redisの値だけを見ても対応するIPを計算しにくくする。4バイトへ縮めるのは、厳密な一意性よりメモリ使用量を優先するためである。異なるIPが同じ32ビット値になる可能性はあるが、その場合はPVが一つ少なく数えられるだけであり、投稿データの安全性には影響しない。

Frontendは、投稿IDとフィンガープリントを結合した値にもHMAC署名を付ける。

```text:small
HMAC-SHA256(shared secret, POST_ID + "\n" + fingerprint)
```

Backendは署名を検証できた場合だけPVを記録する。公開Backend APIへ直接アクセスしたクライアントが、任意のフィンガープリントを大量に作ってカウンタを増やすことを難しくするためである。現在の実装では共有秘密として ``STGY_REDIS_PASSWORD`` を利用する。

転送元ヘッダをIPの正本として使うため、実運用ではCaddyなどの信頼するリバースプロキシがこれらのヘッダを設定し、外部クライアントからの偽装値をそのまま採用しない構成が前提になる。

## 投稿別LRUによる重複排除

投稿ごとに、最近見たフィンガープリントを最大150件保持する。Redis Stringの値へ、4バイトの値をそのまま連結する。

```text:small
古い ← [4 bytes][4 bytes][4 bytes] ... [4 bytes] → 新しい
```

最大サイズは次の通りである。

```text:small
4 bytes × 150 = 600 bytes / post
```

同じフィンガープリントが再び来た場合は、既存位置から取り除いて末尾へ移動するが、PVは加算しない。新しいフィンガープリントなら末尾へ追加し、150件を超えた分だけ先頭から捨てて、PVを1増やす。

これは10日間の全IPを厳密に覚える仕組みではない。ある投稿へ150種類を超えるIPからアクセスがあれば、古いフィンガープリントは追い出され、そのIPからの再訪が後で新規PVとして数えられる。また、LRUキーが期限切れになった後の再訪も新規PVになる。人気の傾向を小さなメモリで見るための近似である。

LRUのTTLは11日で、アクセスされるたびに更新される。投稿へ長期間アクセスがなければ、重複排除データは自動的に消える。

## Redisのデータ構造

PV集計に使う主なRedisキーは以下の通りである。

### 日次投稿別PV

```text:small
stgy:pub-views:daily:{ownerId}:{YYYYMMDD}
```

所有者とUTC日付ごとに一つのHashを作る。fieldは投稿ID、valueはその日の重複排除後PVである。

```text:small
19FD706DCB600000 -> 138
19FD705B39100000 -> 42
```

一アクセスごとのレコードではないので、PVが100万回あっても、その日の同じ投稿について増えるのはHash fieldの整数値だけである。日次キーは11日目に期限切れになる。

### 投稿別LRU

```text:small
stgy:pub-views:lru:{ownerId}:{postId}
```

値は最大600バイトのフィンガープリント列である。

### Stats用メタデータ

```text:small
stgy:pub-views:meta:{ownerId}:{postId}
```

値には、公開日時と150文字のプレーンテキストダイジェストをJSONで保存する。

```json:small
{
  "publishedAt": "2026-08-06T12:22:58.000Z",
  "digest": "STGYの記事外部公開機能では、公開日時を正本として…"
}
```

ダイジェストは、すでに投稿へ保存されているJSONスニペットから生成する。Statsを表示するたびにPostgreSQLから最大1000記事を読み出さないための最小情報である。メタデータは、署名済みアクセスが来るたびに更新されるので、同一IPによる重複アクセスでPVが増えない場合でも、公開日時とダイジェストは新しい内容へ更新できる。

Popular entriesのリッチなスニペットはRedisへ保存しない。Redisから得るのは順位付きIDとPVだけであり、表示時に ``POST /posts/pub-by-ids`` へID配列を渡して、通常のPostデータをPostgreSQLから一括取得する。Stats用の小さなメタデータと、公開ページ表示用の正規の投稿データを分けている。

### 集計キャッシュ

```text:small
stgy:pub-views:ranking:{ownerId}
stgy:pub-views:stats:{ownerId}
```

ランキングとStatsの計算結果は5分間キャッシュする。アクセスが来るたびにキャッシュを削除すると、人気記事へのアクセスが多いほど再集計が増えるので、最大5分の表示遅延を許容する。PVが0の空結果はキャッシュせず、最初のアクセスが来た直後に古い空キャッシュを見続けないようにする。

## Luaによる原子的更新

同じ投稿へ複数のアクセスが同時に来た場合、Backendで ``GET``、判定、``SET``、``HINCRBY`` を別々に行うと競合が起きる。二つのリクエストが同じ古いLRUを読み、両方とも新規と判断してPVを二回加算する可能性がある。

そこで、次の処理を一つのRedis Luaスクリプトで実行する。

1. 投稿別LRUを読む。
2. 値が4バイト単位でない、または上限より大きい場合は破損値として捨てる。
3. 対象フィンガープリントを既存列から取り除く。
4. 末尾へ追加する。
5. 600バイトを超えた先頭部分を捨てる。
6. LRUとメタデータをTTL付きで保存する。
7. フィンガープリントが既存でなかった場合だけ、日次Hashを ``HINCRBY`` する。
8. 日次Hashの期限を設定する。

```text:small
LRU更新
＋ 重複判定
＋ 日次PV加算
＋ TTL設定
＋ メタデータ更新
       ↓
一回のLua実行
```

Redisは一つのLuaスクリプトを他のコマンドと割り込ませずに実行するため、LRUとPVの整合性を保てる。追加モジュールは不要で、ioredisの ``defineCommand`` から必要になった時点で登録して呼び出す。

## 直近10日間の集計

ランキングキャッシュがない場合、当日を含む直近10日分の日次Hashを読み出す。10回の ``HGETALL`` はRedis pipelineへまとめる。各日のfieldを投稿IDごとにMapへ足し合わせると同時に、サイト全体のPV合計も計算する。

```text:small
日次Hash 1 ┐
日次Hash 2 ├─ 投稿IDごとに合算 ─→ 10日間PV
    ...     │
日次Hash 10┘
```

投稿別Statsは最大1000件でよいが、全投稿を完全に並べ替える必要はない。サイズ1000の最小ヒープを使い、現在の上位1000件だけを保持する。

```text:small
N = 10個の日次Hashにあるfield数の合計
U = 異なる投稿数
K = 1000
```

計算量は次の通りである。

```text:small
日次カウンタの合算  O(N)
上位K件の選択       O(U log K)
上位K件の整列       O(K log K)
```

Kは1000の固定値なので、全体は実質的に日次Hashのfield数へ比例する。PV数そのものには比例しない。ある投稿が一日に100万PVを得ても、一日分のHashでは一つのfieldである。

全ページPVは、上位1000件へ入らなかった記事も含めて合算する。投稿別一覧だけを1000件へ制限しているので、PublicationsのTotal page viewsは直近10日分の全カウンタの合計になる。

## PublicationsのStats

PublicationsページのStatsタブは、ログイン中の本人または管理者だけが取得できる ``GET /users/{id}/pub-stats`` を使う。公開ページから必要なPopularランキングとは分け、150文字ダイジェストを含む詳細統計を第三者へ無制限に公開しない。

Statsには次を表示する。

- 直近10日間のTotal page views
- 投稿IDと公開日時
- Contentのプレーンテキストダイジェスト
- 投稿別PV

投稿別一覧は最大1000件を一度取得し、Frontend上でID、公開日時、PVの順序を切り替える。並べ替えるたびにRedisを再集計しない。表は一ページ50件に分割し、ページ番号をURLの ``?page=`` に保持する。

Stats用メタデータがRedisから期限切れになった投稿は、投稿別一覧から一時的に欠けることがある。一方、日次Hashに残っているPVはTotal page viewsへ含まれる。次にその投稿が閲覧されればメタデータが再作成される。

## Popular entries

Popular entriesでは、Frontendがまず次の公開APIを呼ぶ。

```text:small
GET /users/{ownerId}/pub-ranking?limit=5
```

返すのはIDとPVだけである。

```json:small
[
  { "id": "19FD706DCB600000", "pv": 138 },
  { "id": "19FD705B39100000", "pv": 42 }
]
```

そのID配列を ``POST /posts/pub-by-ids`` へ渡して、入力順を維持した公開Postを取得する。記事ページのRecent postsもPopular entriesも最終的には同じPost型と同じJSONスニペット描画を使う。異なるのは投稿の選び方だけである。

```text:small
Recent posts
  PostgreSQLのpublished_at順で選ぶ

Popular entries
  RedisのPV順でIDを選ぶ

共通部分
  Post.snippetを記事スニペットとして描画する
```

Recent postsとPopular entriesの取得には依存関係がないため、公開記事ページでは両方を並行して取得する。Popularランキングの取得に失敗しても記事本文とRecent postsは表示し、Popular entriesだけを空にする。

## 負荷と保存量

一つの公開記事表示で、PV記録に関して発生する主要処理は次の通りである。

```text:small
Frontend
  User-Agent判定
  IPのHMACと署名生成

Backend
  署名検証
  Redis Luaを1回実行
```

Luaの中では投稿別LRUを最大600バイト走査し、必要なら日次Hashを1加算する。PostgreSQLへアクセスログのINSERTは行わない。投稿本文の取得は公開ページ表示に元から必要な処理であり、カウンタのための追加DB書き込みはない。

Redisの保存量は、おおむね次の要素で決まる。

- 閲覧された投稿ごとに最大600バイトのLRUとキーのオーバーヘッド
- 閲覧された投稿ごとに公開日時と短いダイジェスト
- 所有者、日付、閲覧された投稿の組ごとに日次Hashのfield一つ
- 所有者ごとの5分間ランキングキャッシュとStatsキャッシュ

アクセス件数そのものを保存しないので、同じ投稿へのPVが増えてもRedisメモリはほぼ増えない。メモリ量は「直近に閲覧された投稿数」と「日ごとにPVが発生した投稿数」に比例する。

## 制限と割り切り

現在の外部公開とアクセスカウンタには以下の制限がある。

- 外部公開は投稿の現在内容を表示し、公開時点の版を保存しない。公開後の編集も即座に反映される。
- ``published_at`` をnullへ戻すと外部から取得できなくなるが、Redisの過去PVは期限まで残り得る。
- PVは直近10日間だけで、累積PVを永続保存しない。
- Redisを消去するとStatsとPopular entriesは失われる。
- 同一IP判定は投稿別の直近150フィンガープリントだけであり、厳密なユニーク閲覧者数ではない。
- 32ビットフィンガープリントの衝突により、異なるIPを同一とみなす可能性がある。
- 150種類を超えるアクセスやLRUの期限切れ後には、同じIPが再び数えられる。
- User-Agentを偽装するボットは通常アクセスとして数えられる。
- ランキングとStatsは5分キャッシュされるため、最新PVの反映には遅延がある。
- 転送元IPヘッダは、信頼するリバースプロキシが正しく設定する必要がある。
- 高度なアクセス解析に必要な参照元、地域、端末、閲覧経路などは記録しない。

これらは不具合ではなく、アクセス履歴を永続化せず、単一ホストでも小さな負荷でPopular entriesと短期Statsを提供するための選択である。広告課金、厳密なユニークユーザ数、長期分析が必要な運用では、専用のアクセス解析基盤を別途導入すべきである。

## まとめ

STGYの記事外部公開機能は、``posts.published_at`` を公開状態の正本とし、SNS内部の投稿を別データへ複製せずに、``/sites/{userId}`` と ``/pub/{postId}`` へブログ風に表示する。公開記事APIは現在時刻以前の投稿だけを返し、サイト一覧、記事詳細、前後記事、ID集合取得を用途ごとに分ける。Markdown本文とJSONスニペットは内部表示と共用し、外部ページ側ではサイト設定、デザインテーマ、OGP、ページネーション、プロフィール、Recent postsを組み合わせる。

アクセスカウンタは、生のIPアドレスや個々のアクセス履歴を保存しない。Frontendで自己申告ボットを除外し、IPを鍵付きハッシュの32ビットフィンガープリントへ変換し、Backendで署名を検証する。Redis Luaが投稿別LRUの更新、重複判定、日次PV加算、TTL設定、Stats用メタデータ更新を一回で行う。

直近10日間のランキングは、所有者ごとの日次Hashを合算し、固定サイズ1000の最小ヒープで上位投稿を選ぶ。StatsはRedisの短いダイジェストを使い、Popular entriesはランキングIDを汎用の ``pub-by-ids`` へ渡してPostgreSQLから正規の投稿データを一括取得する。PV数ではなく閲覧された投稿数に主に比例する構成なので、単純なアクセスカウンタのために大きな履歴テーブルを運用せずに済む。

外部公開はSNSの投稿を別の読者へ届ける表示層であり、アクセスカウンタはその表示層へ必要最小限の観測機能を加える補助層である。正本は常にPostgreSQLの投稿と公開設定に置き、消えても再構築または再蓄積できる短期統計だけをRedisへ置くことで、機能と運用コストを分離している。
