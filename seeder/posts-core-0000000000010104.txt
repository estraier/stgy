# Analysis of STGY's Major Queries

This article analyzes the queries issued to the database during STGY operation. It presents concrete SQL examples, analyzes their computational complexity, and verifies the analysis by examining actual execution plans.

The scope of fixes in this review is limited to places where the original SQL does not guarantee its intended asymptotic complexity in the form of the SQL itself, and places where paging can omit results. Rewrites that merely reduce execution time or buffer references for a particular validation dataset are not adopted.

The execution plans below target the validation database created by ``npm run reset-data-volume-test``. In addition to the existing initial data, ``make-volume-test.py`` inserts one measurement user and 30,000 dummy users with reproducible IDs and timestamps. User activity follows a long-tail distribution: 12,000 users with no posts, 12,000 with one post, 4,500 with three posts, 1,350 with ten posts, and 150 with fifty posts. It also adds 20,000 root posts for user00001 to model a long-term, high-volume user, and 15,000 replies by user00002 to the first benchmark post to model a viral post, for a total of 81,502 measurement posts. With the existing 15 initial posts, the posts table contains 81,517 rows in total.

Follow relationships are not made fully reciprocal either. An ordinary user deterministically follows four popular accounts and eight nearby users. The measurement user user00000 follows 5,000 users and is followed by 20,000 users, making it a high-degree user. This produces a distribution containing many low-degree users, popular users with hundreds to thousands of followers, and one outstanding high-degree user. The first benchmark post receives 20,000 likes, and the measurement user likes the latest post of each followed user who has at least one post. One in five dummy users is an AI user, for a total of 6,000 AI users. The search-index update queue receives 30,000 user tasks and 1,000 post tasks so that a backlog with one task type concentrated near the front is also reproduced. Finally, 1,000 event-log entries and 15,000 unread plus 15,000 read notifications for the measurement user are inserted.

Finally, PostgreSQL ``ANALYZE`` is run, so the SQL in this article can be executed immediately afterward. The script also prints the cursor IDs and actual row counts used in each comparison. The measurement user's ID is 1853070350746583040 and its nickname is user00000. For measurements where JIT compilation time could contaminate a short OLTP query, specify ``SET jit = off`` in the session.

## The Simplest Example
Consider retrieving the latest 20 posts from all posts. The following query is not actually used; it is a simplified example for explanation. By default, the list excludes replies, so the condition that reply_to is NULL is added.

```sql:small
SELECT
  p.id, p.owned_by, p.reply_to,
  p.allow_likes, p.allow_replies, p.updated_at
FROM posts p
WHERE p.reply_to IS NULL
ORDER BY p.id DESC OFFSET 0 LIMIT 20;
```

The posts table has a partial index on IDs that covers only rows whose reply_to is NULL, so the operation can be completed by scanning that index. Let the total number of posts be P. Finding the starting point costs O(log(P)), and reading the following 20 rows takes constant time. This means that even if P becomes enormous, the amount of work does not grow in proportion to the total number of posts.

To inspect the execution plan with the current schema and data, run the following. Execution time and row counts vary with data volume, statistics, and cache state, so record the output in the result section immediately following the command.

```sql:small
EXPLAIN (ANALYZE, BUFFERS)
SELECT
  p.id, p.owned_by, p.reply_to,
  p.allow_likes, p.allow_replies, p.updated_at
FROM posts p
WHERE p.reply_to IS NULL
ORDER BY p.id DESC OFFSET 0 LIMIT 20;
```

```:small
 Limit  (cost=0.29..2.11 rows=20 width=34) (actual time=0.035..0.044 rows=20 loops=1)
   Buffers: shared hit=3
   ->  Index Scan Backward using idx_posts_root_id on posts p  (cost=0.29..5671.22 rows=62475 width=34) (actual time=0.033..0.040 rows=20 loops=1)
         Buffers: shared hit=3
```

In the measurement, PostgreSQL scanned ``idx_posts_root_id`` backward and stopped as soon as it obtained 20 rows. There was no additional Sort; three buffer pages were referenced, and execution time was 0.091 ms. As long as the returned row count is fixed at 20, no scan proportional to the total number of posts occurs.

## listPosts
In real operation, the result also needs attributes from other tables: author user IDs must be resolved to names, and tag information and counters attached to each post must be included. This is implemented by the backend method postsService.listPosts. When reply_to is NULL and focusUserId is not specified, the query is as follows.

```sql:small
SELECT
  p.id, p.owned_by, p.reply_to, p.published_at, p.updated_at,
  p.snippet, p.locale, p.allow_likes, p.allow_replies,
  id_to_timestamp(p.id) AS created_at,
  u.nickname AS owner_nickname,
  u.locale AS owner_locale,
  pp.owned_by AS reply_to_owner_id,
  pu.nickname AS reply_to_owner_nickname,
  COALESCE(pc.reply_count, 0) AS count_replies,
  COALESCE(pc.like_count, 0) AS count_likes,
  ARRAY(SELECT pt2.name FROM post_tags pt2
    WHERE pt2.post_id = p.id ORDER BY pt2.name) AS tags
FROM posts p
JOIN users u ON p.owned_by = u.id
LEFT JOIN posts pp ON p.reply_to = pp.id
LEFT JOIN users pu ON pp.owned_by = pu.id
LEFT JOIN post_counts pc ON pc.post_id = p.id
WHERE p.reply_to IS NULL
ORDER BY p.id DESC OFFSET 0 LIMIT 20;
```

As in the simplest example, the query first narrows the result set to 20 posts using the partial post-ID index, then enriches those 20 rows by consulting users, posts, post_counts, and post_tags. If focusUserId is specified, a column is also added to determine whether the author has blocked that user. After the list is obtained, two additional batched queries, restricted to the returned post IDs, determine whether that user has liked or replied to each post.

Now consider the complexity. Let U be the total number of users and P the total number of posts. First, if the index is effective, obtaining the matching post list costs O(log(P)) + O(20). Since 20 is a constant, this is O(log(P)). For each of the 20 hits, the query then resolves counters, tags, and user names. If primary-key or composite-primary-key indexes are effective on each joined table, the 20 rows remain a constant, so the dominant term is O(log(P)) or O(log(U)). Assuming U is sufficiently smaller than P, the dominant term for the whole operation is O(log(P)).

## listPostsByFollowees
A typical STGY view as an SNS is the list of posts by users you follow. This is also the default view immediately after login. It is fair to say that the performance of an SNS depends heavily on whether this query can be processed efficiently.

The basic strategy is to exploit the fact that the display count is a constant 20. By default, the frontend selects at most 20 recently active users, including the current user, and takes the latest three posts from each, limiting the candidate set to at most 60 posts. Expressed with concrete values, the actual query is as follows. This example includes replies.

```sql:small
WITH
all_followers AS (
  SELECT followee_id
  FROM user_follows
  WHERE follower_id = 1853070350746583040
  UNION
  SELECT 1853070350746583040
),
active_followers AS (
  SELECT af.followee_id AS owned_by, latest_post.id AS last_id
  FROM all_followers af
  JOIN LATERAL (
    SELECT p2.id
    FROM posts p2
    WHERE p2.owned_by = af.followee_id
    ORDER BY p2.id DESC
    LIMIT 1
  ) AS latest_post ON TRUE
),
top_followees AS (
  SELECT owned_by
  FROM active_followers
  ORDER BY last_id DESC
  LIMIT 20
),
candidates AS (
  SELECT pid.id
  FROM top_followees tf
  JOIN LATERAL (
    SELECT p2.id
    FROM posts p2
    WHERE p2.owned_by = tf.owned_by
    ORDER BY p2.id DESC
    LIMIT 3
  ) AS pid ON TRUE
),
top_posts AS (
  SELECT id
  FROM candidates
  ORDER BY id DESC
  OFFSET 0
  LIMIT 20
)
SELECT
  p.id, p.owned_by, p.reply_to, p.published_at, p.updated_at,
  p.snippet, p.locale, p.allow_likes, p.allow_replies,
  id_to_timestamp(p.id) AS created_at,
  u.nickname AS owner_nickname,
  u.locale AS owner_locale,
  pp.owned_by AS reply_to_owner_id,
  pu.nickname AS reply_to_owner_nickname,
  COALESCE(pc.reply_count, 0) AS count_replies,
  COALESCE(pc.like_count, 0) AS count_likes,
  ARRAY(SELECT pt2.name FROM post_tags pt2
    WHERE pt2.post_id = p.id ORDER BY pt2.name) AS tags
FROM top_posts t
JOIN posts p ON p.id = t.id
JOIN users u ON p.owned_by = u.id
LEFT JOIN posts pp ON p.reply_to = pp.id
LEFT JOIN users pu ON pp.owned_by = pu.id
LEFT JOIN post_counts pc ON pc.post_id = p.id
ORDER BY t.id DESC;
```

The query is fairly involved, so examine it piece by piece.

- Build a view named all_followers containing the IDs of followed users plus the current user's own ID. This is the union of the followed-user IDs and the current user's ID.
- For each user in all_followers, scan the ``(owned_by, id)`` index from the end and obtain only the latest post with LIMIT 1, producing a view named active_followers.
- Sort active_followers by latest post ID and retain the 20 users who posted most recently as top_followees.
- JOIN LATERAL each user ID in top_followees and take up to the latest three post IDs for that user, producing a view named candidates.
- Sort the at most 60 post IDs in candidates and narrow them to the latest 20, producing a view named top_posts.
- For each ID in top_posts, enrich it with the same kinds of attributes as listPosts.

When replies are excluded, ``p2.reply_to IS NULL`` is added to both active_followers and candidates. The API allows the per-user count to be specified with limitPerUser; the frontend default is 3. The block check when focusUserId is specified, and the liked/replied state additions after retrieval, are the same as in listPosts.

The previous active_followers implementation read the posts of all selected followees together and used ``DISTINCT ON (owned_by)`` to select each user's latest post. That SQL left join order and scan range to the planner, so when selected followees owned many posts, the planner could choose a plan whose work was proportional to that post set. The current SQL places each ID from all_followers on the outer side and performs one indexed lookup per user through a LATERAL subquery with ``LIMIT 1``. This SQL shape therefore guarantees that the intended work is proportional to the number of followees F.

Now consider the complexity. Let P be the total number of posts and F the number of followed users. For each followee, retrieving the single latest post from the ``(owned_by, id)`` index has a dominant term of O(F·log(P)). Selecting the top 20 users is a top-N selection from F rows, O(F·log(20)), which can be regarded as O(F). The subsequent processing of at most 60 posts and the final 20 posts is constant. Therefore the dominant term for the whole query is O(F·log(P)). The query does not scan all P posts at once, although its work still grows in proportion to F.

To inspect the current query, run the following. JIT is disabled for this measurement so that JIT compilation time does not contaminate the short OLTP query.

```sql:small

EXPLAIN (ANALYZE, BUFFERS)

  SELECT followee_id
  FROM user_follows
  WHERE follower_id = 1853070350746583040
  UNION
  SELECT 1853070350746583040
),
active_followers AS (
  SELECT af.followee_id AS owned_by, latest_post.id AS last_id
  FROM all_followers af
  JOIN LATERAL (
    SELECT p2.id
```

During validation, a version that changed the set operation adding the current user's ID to ``UNION ALL`` was also considered. Under the constraint that self-following is prohibited, this is merely a constant-factor change that relies on the absence of duplicates, so it is unnecessary for the complexity fix and was not included in the final version. The per-followee index lookup still occurs F times, so at a scale where the index working set no longer fits in memory and the OS page cache, random I/O will affect performance; that is a capacity issue distinct from the intended asymptotic complexity.

## BuildSearchSeedForUser

BuildSearchSeedForUser, which builds an AI user's interests, also selects recently active users among its followees. Previously it read the followees' posts together and used ``DISTINCT ON (owned_by)`` to select each user's latest post, so the planner could choose work proportional to the size of the followees' post set. It now uses the same shape as listPostsByFollowees and performs only one indexed lookup for the latest post of each followee_id.

```sql:small
followees AS (
  SELECT uf.followee_id
  FROM user_follows uf
  WHERE uf.follower_id = $1
),
active_followees AS (
  SELECT f.followee_id AS owned_by, latest_post.id AS last_id
  FROM followees f
  JOIN LATERAL (
    SELECT p2.id
    FROM posts p2
    WHERE p2.owned_by = f.followee_id
    ORDER BY p2.id DESC
    LIMIT 1
  ) AS latest_post ON TRUE
),
top_followees AS (
  SELECT owned_by AS followee_id
  FROM active_followees
  ORDER BY last_id DESC
  LIMIT 25
)
```

If F is the number of followees and P the number of posts, the dominant term of active_followees is O(F·log(P)). The number of followees selected afterward is fixed at 25, and the number of posts and likes read per followee is also capped. Here too, the only necessary change was from ``DISTINCT ON`` to per-followee LIMIT 1; the way the followee set itself is constructed was not changed.

## listUsers
The implementation named usersService, which operates on the users table, also contains various methods that each issue queries. Most are lightweight, but listUsers, which displays a list of users, requires some care. For example, the social-order query that filters by a nickname prefix while giving priority to followees or followers is as follows.

```sql:small
SELECT
  u.id, u.updated_at, u.snippet, u.nickname, u.avatar,
  u.ai_model, u.is_admin, u.is_frozen, u.block_strangers,
  id_to_timestamp(u.id) AS created_at,
  COALESCE(uc.follower_count, 0) AS count_followers,
  COALESCE(uc.followee_count, 0) AS count_followees,
  COALESCE(uc.post_count, 0) AS count_posts
FROM users u
LEFT JOIN user_counts uc ON uc.user_id = u.id
LEFT JOIN user_follows f1 ON
  f1.follower_id = 1853070350746583040 AND f1.followee_id = u.id
LEFT JOIN user_follows f2 ON
  f2.follower_id = u.id AND f2.followee_id = 1853070350746583040
WHERE LOWER(u.nickname) LIKE 'user00%'
ORDER BY
  (u.id = 1853070350746583040) DESC,
  (f1.follower_id IS NOT NULL) DESC,
  (f2.follower_id IS NOT NULL) DESC,
  u.id ASC OFFSET 0 LIMIT 20;
```

email is stored in the user_secrets table and is not returned by ordinary user-list queries. The current list joins user_counts so that follower count, followee count, and post count are also returned. If focusUserId is specified, after the list above is obtained, a query restricted to the returned IDs checks follow relationships and blocking relationships in both directions in one batch and adds the results.

A prefix match using the LIKE operator can use the ``LOWER(nickname) text_pattern_ops`` index to narrow the candidates. The filtered rows are then ranked in social order, so it is fast when the number of hits is small. If the search string is short and many rows match, all of those candidates must be scored and sorted, increasing the amount of work.

## listFriendsByNicknamePrefix

Nickname autocomplete returns candidates in the order: the current user, followed users, then all other users. The backend method usersService.listFriendsByNicknamePrefix computes K=offset+limit, the number required for paging, collects the current user and followees into preferred, and fills any shortfall from others.

For followees, the implementation does not start from all users matching the nickname and then check follow relationships. Instead, it enumerates followees from user_follows and probes the users primary key for each followee_id. A concrete example is the following query.

```sql:small
WITH
self AS (
  SELECT 0 AS prio, u.id, lower(u.nickname) AS nkey
  FROM users u
  WHERE u.id = 1853070350746583040
    AND lower(u.nickname) LIKE 'user00%'
),
followees AS (
  SELECT 1 AS prio, fu.id, fu.nkey
  FROM user_follows f
  JOIN LATERAL (
    SELECT u.id, lower(u.nickname) AS nkey
    FROM users u
    WHERE u.id = f.followee_id
      AND u.id <> 1853070350746583040
      AND lower(u.nickname) LIKE 'user00%'
    LIMIT 1
  ) AS fu ON TRUE
  WHERE f.follower_id = 1853070350746583040
  ORDER BY fu.nkey USING ~<~, fu.id
  LIMIT 20
),
preferred AS MATERIALIZED (
  SELECT * FROM self
  UNION ALL
  SELECT * FROM followees
),
others AS (
  SELECT 3 AS prio, u.id, lower(u.nickname) AS nkey
  FROM users u
  WHERE u.id <> 1853070350746583040
    AND lower(u.nickname) LIKE 'user00%'
    AND NOT EXISTS (
      SELECT 1
      FROM user_follows f
      WHERE f.follower_id = 1853070350746583040
        AND f.followee_id = u.id
    )
  ORDER BY lower(u.nickname) USING ~<~, u.id
  LIMIT (
    SELECT GREATEST(0, 20 - COUNT(*))
    FROM preferred
  )
),
candidates AS (
  SELECT * FROM preferred
  UNION ALL
  SELECT * FROM others
),
page AS (
  SELECT id, prio, nkey
  FROM candidates
  ORDER BY prio, nkey USING ~<~, id
  OFFSET 0
  LIMIT 20
)
SELECT
  u.id, u.updated_at, u.snippet, u.nickname, u.avatar,
  u.ai_model, u.is_admin, u.is_frozen, u.block_strangers,
  id_to_timestamp(u.id) AS created_at,
  COALESCE(uc.follower_count, 0) AS count_followers,
  COALESCE(uc.followee_count, 0) AS count_followees,
  COALESCE(uc.post_count, 0) AS count_posts
FROM page p
JOIN users u ON u.id = p.id
LEFT JOIN user_counts uc ON uc.user_id = u.id
ORDER BY p.prio, p.nkey USING ~<~, u.id;
```

Previously, followees was an ordinary join between user_follows and users, so the planner could choose not only a plan that starts from F followees, but also a plan that reads matching users from the nickname index and checks the follow relationship for each candidate. If the number of matching candidates is M, the latter is O(M·log(F)) in the worst case and does not provide the intended O(F·log(U)) behavior when M approaches U. The LATERAL subquery explicitly performs a primary-key lookup for each followee_id in order to fix this join direction.

Retrieving the current user by the users primary key costs O(log(U)). If F is the number of followees, the followees branch enumerates F rows from user_follows and probes the users primary key for each, giving a dominant term of O(F·log(U)). The nickname-prefix condition is evaluated on each followee row obtained through the primary key. Work proportional to F remains, but the query does not search for followees starting from all users whose nicknames match.

only when preferred does not reach K rows is others executed. ``idx_users_nickname_id`` is the composite index ``LOWER(nickname) text_pattern_ops, id``. Writing ``ORDER BY lower(nickname) USING ~<~, u.id`` allows candidates to be read in that index order and the scan to stop as soon as the required number of rows has been obtained. Because candidates that are the current user or a followee are excluded, the number actually inspected also depends on the selectivity of the search term and the distribution of follow relationships.

## fetchBatch
When the worker that creates notifications reads the event log, it executes a query like the following.

```sql:small
SELECT
  event_id, payload::json AS payload
FROM event_logs
WHERE partition_id = 0
  AND event_id > 1869468402083381248
ORDER BY event_id ASC
LIMIT 100;
```

Because the primary key is the composite key of partition_id and event_id, using that index should yield an efficient plan. If E is the number of event-log rows, finding the starting point costs O(log(E)), and reading at most the following 100 rows takes constant time. Because partition_id is specified by equality, there is no need to repeat partition_id in ORDER BY.

There is a trap in this query. If event_id is given a B-tree unique constraint to make it searchable by itself, the planner may choose to scan the target event_id range through that index while filtering for the desired partition_id. In the current schema, a hash index is used for event_id-only lookup, while batch retrieval uses the composite primary key.

## Current Complexity Concerns and Mitigation Status

In addition to the individual queries above, the entire codebase was reviewed to see how the amount of work grows as the numbers of users, posts, documents, and queued tasks increase. The concern here is not simply whether execution time or a constant factor can be reduced, but whether a path performs a full scan or quadratic work for its intended use and therefore becomes impractical as the dataset grows.

### Full-Table Traversal by the AI User Worker

The AI-user worker fetches unfrozen AI users in fixed-size batches and processes them in order. Previously it increased OFFSET as follows.

```sql:small
SELECT u.id, u.nickname, u.is_admin, u.ai_model
FROM users u
WHERE u.ai_model IS NOT NULL
  AND u.is_frozen = FALSE
ORDER BY u.id ASC
LIMIT 200 OFFSET 15000;
```

Let A be the total number of users whose ai_model is set and B the batch size. Even if frozen users are excluded from the result, the number of rows skipped while traversing all rows from the beginning is ``0 + B + 2B + ...``. Thus, ignoring index-seek cost, the total row scan alone is O(A² / B), so the work required for one full pass grows quadratically as the number of AI users increases.

This was changed to keyset pagination, passing the ID of the last row obtained in the previous batch as the cursor.

```sql:small
SELECT u.id, u.nickname, u.is_admin, u.ai_model
FROM users u
WHERE u.ai_model IS NOT NULL
  AND u.is_frozen = FALSE
  AND u.id > 1853160963440578560
ORDER BY u.id ASC
LIMIT 200;
```

``users`` has the partial index ``idx_users_ai_id`` on ``id WHERE ai_model IS NOT NULL``. Because is_frozen is not part of the index condition, frozen AI users are still traversed in the index and removed by Filter, but each batch seeks to its cursor position in the B-tree and continues forward. Therefore the total number of AI-user rows actually traversed in one full pass is O(A). Including the seek for each batch, the whole operation is ``O(A + (A / B)·log(A))``, avoiding the previous quadratic behavior. The existing OFFSET-based list API is retained for compatibility, and only the AI-user worker uses ``order=asc`` with ``after``.

The validation data includes 6,000 AI users, all with is_frozen false. To compare the previous deep OFFSET with the new keyset pagination, run the following. ### Search-Index Update Queue

The search-index update worker runs independent loops for posts and users, and each loop retrieves a constant number of the oldest tasks with the following query.

```sql:small
SELECT id, name_prefix, doc_id, body_text, locale, doc_timestamp
FROM search_indexing_tasks
WHERE name_prefix = 'posts'
ORDER BY id ASC
LIMIT 100;
```

Previously there was only the primary key on ``id``. Consequently, if a large backlog of tasks for another ``name_prefix`` accumulated near the front of ID order, finding the desired tasks could require inspecting a number of rows proportional to the total queue size Q. In particular, an unsuccessful poll when no task for the target prefix exists could be O(Q) in the worst case.

To avoid this, the following composite index was added.

```sql:small
CREATE INDEX idx_search_indexing_tasks_name_prefix_id
ON search_indexing_tasks(name_prefix, id);
```

This allows PostgreSQL to seek to the beginning of the target prefix in O(log(Q)) and then retrieve at most B rows in ID order. A single fetch becomes ``O(log(Q) + B)`` and does not grow with the backlog size of another prefix.

To compare the same data distribution with and without the composite index, run the following. The validation data contains 30,000 user tasks at the front of ID order followed by 1,000 post tasks. Dropping and recreating the index is done inside a transaction, with a final ``ROLLBACK``.

### Full Traversal for Post Export

The frontend process that exports all posts by a user previously traversed to the end by increasing the OFFSET of ``listPosts`` in batches of 200. If N is the number of the user's posts and B the batch size, the total number of rows skipped is ``0 + B + 2B + ...``, making a full retrieval O(N² / B).

A backward-compatible ``after`` parameter was added to ``listPosts``. In descending order, it obtains posts whose IDs are smaller than the final post ID of the previous batch, as follows.

```sql:small
SELECT p.id
FROM posts p
WHERE p.owned_by = 1853070350746583040
  AND p.id < 1855878856704991232
ORDER BY p.id DESC
LIMIT 200;
```

Because ``posts`` has the composite index ``idx_posts_owned_by_id`` on ``(owned_by, id)``, each batch can seek to the cursor position in O(log(P)) and read only the next B rows. A full traversal therefore becomes ``O(N + (N / B)·log(P))``. ``order=asc`` uses ``id > after`` and ``order=desc`` uses ``id < after``; the OFFSET path is retained for existing clients. The export process was changed to use ``order=desc`` with ``after``.

### Other Concerns and Their Current Treatment

* General list APIs still support OFFSET pagination. Deep pages skip rows in proportion to offset, but the normal UI is not realistically used to step sequentially through thousands of pages, so this differs from a worker that must traverse every row. ``listUsers`` and ``listPosts`` now also support backward-compatible keyset pagination through ``after``: ``order=asc`` uses ``id > after`` and ``order=desc`` uses ``id < after``. The previous OFFSET path remains for existing clients. In the frontend user list, the All tab and nickname-filtered list that use ``listUsers`` store the final ID of the previous page in the session and use it as ``after`` to retrieve the next page. If a page number with no corresponding cursor is opened directly from a URL, the code falls back to the previous OFFSET behavior. Full-text search uses ``searchUsers``, while Followees and Followers use separate APIs, so they are not covered by this ``after`` mechanism. The social ordering of ``listUsers`` cannot represent its cursor with an ID alone and is therefore excluded from ``after``. Other general list APIs are left unchanged for now.
* Body-text search using PostgreSQL ``ILIKE '%...%'`` and exact ``COUNT(*)`` scale with the number of matching rows. Both are currently administrative functions, while public full-text search is separated into TTTS, so they are left unchanged for now.
* Nickname autocomplete does not use the social-order ``listUsers`` search, which can have many candidates; it uses the dedicated ``listFriendsByNicknamePrefix`` instead. Therefore broad social prefix matching is no longer on the ordinary UI autocomplete path.
* The followees branches of ``listPostsByFollowees``, ``BuildSearchSeedForUser``, and ``listFriendsByNicknamePrefix`` scale with the number of followees F. This follows the current design for avoiding scans of all posts or all users, and their dominant terms are O(F·log(P)) or O(F·log(U)). If F becomes extremely large, possible measures include a cap, preselection of important followees, or caching the active set and results.
* For the focusUserId liked-state check, the ``liked_by``-side index was selected for a user with few likes, while the composite primary key ``(post_id, liked_by)`` was selected for a user with many likes. In the latter case, both conditions appeared in ``Index Cond`` and an Index Only Scan could be performed for at most 20 candidate posts. Because an appropriate index is selected according to the data distribution, no additional change is made.
* TTTS search examines newer chronological shards first and stops as soon as it has enough results. It also has a depth limit, timeout, and Redis cache. The possibility of examining multiple shards in the worst case is accepted as part of the specification, so no change is made at this time.

Thus, the complexity defects fixed through this review are three: OFFSET in the full traversal of AI users, the absence of a composite index for the search-index update queue, and full post-export traversal using OFFSET. The remaining cases are classified as administrative functions with limited use, deep pagination used only by the normal UI, or known linear behavior accepted by design, and will be reconsidered if they become actual operational problems.

## Overall Assessment

As seen above, for ordinary list displays the schema and queries are designed to narrow candidate article IDs or user IDs first using indexes wherever possible. As long as the relevant indexes fit in memory cache, fast random access can be expected. Some paths still scale with the number of hits or followees, such as body-text ``ILIKE '%...%'`` and operations that inspect all followees. The social-order ``listUsers`` query for a short nickname prefix is not used for autocomplete; it has been replaced there with the dedicated ``listFriendsByNicknamePrefix``. Public full-text search uses an external search service so that its load is separated from PostgreSQL.

listPosts, used to display the latest posts globally, can obtain a constant number of rows from indexes under ordinary ID and tag conditions. Full export uses ``after`` with ``idx_posts_owned_by_id`` for keyset pagination. The focusUserId replied-state check uses the composite posts index on reply_to and owned_by. For the liked-state check, the ``liked_by``-side index is selected for a user with few likes and the composite primary key of ``post_likes`` for a user with many likes; in the latter case both ``post_id`` and ``liked_by`` were confirmed to appear in ``Index Cond``. listPostsByFollowees, used to list the latest posts by followed users, and active_followees in BuildSearchSeedForUser, which builds an AI search seed, both perform only one indexed lookup for the latest post of each followee, so the dominant term is O(F·log(P)). listPostsLikedByUser can also obtain a constant number of rows from the liked_by/created_at index. The followees branch of listFriendsByNicknamePrefix enumerates F followees and looks each user up by primary key, making its dominant term O(F·log(U)). If preferred is insufficient, the others branch scans the nickname index in order and stops when it has enough rows for the page. However, ILIKE body-text search does not have the same guarantee with respect to the total row count. Neither does social-order listUsers with a large candidate set, but that query is no longer used for nickname autocomplete.

All EXPLAIN results covered in this article were reviewed. The current queries satisfy the configured requirements: ordinary SNS screens first narrow the result set to a constant number of rows; full traversals use keyset pagination; feeds and autocomplete start from the number of followees rather than the total number of posts or users; and worker queue retrieval does not scan the backlog of another task type. Only the comparison queries that intentionally removed an index or deliberately mismatched an expression scanned all rows or a large candidate set, also confirming the effect of the required indexes and SQL forms. Therefore no additional SQL or index changes are required for the current requirements.

Both listPostsByFollowees and the followees branch of listFriendsByNicknamePrefix perform index probes proportional to the number of followees F. The current implementation does not impose a cap such as 200 followees. The others branch of listFriendsByNicknamePrefix can terminate early, but if a short search term matches many users and many of them are the current user or followees, it may inspect more candidates than the number ultimately needed. If these become problems at larger scale, a cap, preselection of target followees, result caching, and similar measures should be considered.

If UX requirements do not permit limiting the number of followees, a practical approach is not to query every followed user on every request but to periodically compute and cache a subset of “important followees” or a set of active users. Even so, the system should retain a correct database query as its foundation so that it can return the right result even when the cache is absent.

Retrieving large data such as post bodies and user-profile text can also become a scalability constraint. Reading a record from the main table by primary key is only O(log(N)) in the number of rows N. Nevertheless, it becomes slower when the data itself is large. Once the data no longer fits in memory cache, each access reaches storage; with HDDs, seek time is added. Large values also increase the volume transferred between storage and memory. Keeping only snippets in posts and users instead of storing full bodies there mitigates this issue. Logarithmic complexity is a fundamental requirement, but optimizations not visible in Big-O notation also make a quiet but important difference in performance.

* Limits

It is worth considering when and how an individual database server will reach its limit—in other words, when and how actual throughput will cease to meet required throughput. For example, if 100 QPS were processed as one strictly serial stream, each request would have to keep finishing within 10 ms on average. Real PostgreSQL can process multiple connections concurrently, so acceptable latency cannot simply be defined as ``1 / QPS``. It must be determined by load tests that include CPU, storage, locks, connection count, and cache competition among queries.

As already described, list queries consist of a phase that uses indexes to narrow the IDs to return and a phase that consults the main tables to enrich each ID with attributes. One trigger for declining performance is when the working set of frequently referenced indexes and table pages no longer fits within PostgreSQL shared_buffers plus the OS page cache, increasing the proportion of physical I/O. Starting with shared_buffers at around 25% of physical memory and tuning from there is common, but that does not mean 25% is always optimal. Both PostgreSQL's buffers and the OS page cache must be considered, and shared_buffers capacity alone is not the performance boundary.

The actual space occupied by tables and indexes can be checked with the following query. Using only ``pg_relation_size`` does not require the pageinspect extension. Once production operation begins, the results should be recorded periodically so that their growth rate can be monitored.

```sql:small
SELECT
  n.nspname AS schema,
  c.relname AS name,
  CASE c.relkind
    WHEN 'r' THEN 'table'
    WHEN 't' THEN 'toast'
    WHEN 'i' THEN 'index'
    WHEN 'm' THEN 'mview'
    ELSE c.relkind::text
  END AS type,
  pg_size_pretty(pg_relation_size(c.oid)) AS size_pretty,
  pg_relation_size(c.oid) / 8192 AS pages_8k
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND c.relkind IN ('r', 't', 'i', 'm')
ORDER BY pages_8k DESC;
```

To extract only the seven post-related indexes, run the following.

```sql:small
SELECT
  c.relname AS name,
  pg_relation_size(c.oid) AS size,
  pg_relation_size(c.oid) / 8192 AS pages_8k
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind = 'i'
  AND c.relname IN (
    'posts_pkey',
    'idx_posts_owned_by_id',
    'idx_posts_reply_to_id',
    'idx_posts_reply_to_owned_by',
    'idx_posts_root_id',
    'idx_posts_root_owned_by_id',
    'idx_posts_public_owned_by_published_at'
  )
ORDER BY c.relname;
```

```:small
                  name                  |  size   | pages_8k
----------------------------------------+---------+----------
 idx_posts_owned_by_id                  | 2605056 |      318
 idx_posts_public_owned_by_published_at | 4472832 |      546
 idx_posts_reply_to_id                  | 2719744 |      332
 idx_posts_reply_to_owned_by            | 1245184 |      152
 idx_posts_root_id                      | 1777664 |      217
 idx_posts_root_owned_by_id             | 1998848 |      244
 posts_pkey                             | 1867776 |      228
```

The seven indexes total 16,687,104 bytes. Dividing by the 81,517 rows in ``posts`` at measurement time gives approximately 204.7 bytes per post for this test-data distribution.

Suppose the machine has 16 GiB of physical memory and ``shared_buffers`` is 4 GiB, and assume half of that can be used for indexes and 80% of the index share can be used for post-related indexes. Then approximately 1.6 GiB is available for post indexes. A simple linear extrapolation of 1.6 GiB divided by about 204.7 bytes corresponds to roughly 8.39 million posts.

This is not a hard limit; it is only a Fermi-estimate-level rule of thumb. The seven indexes do not cover identical row sets, and capacity per post changes with data distribution, B-tree page fill factor, bloat from updates and deletes, and VACUUM state. Real access is biased toward newer posts, so frequently used pages tend to remain cached even if the entire index does not fit. The OS page cache also helps. On the other hand, queries such as listPostsByFollowees that perform random index accesses across many users become more sensitive to physical I/O as the working set widens.

The main tables have a separate cache boundary. Keeping full bodies out of posts and users and storing only snippets and attributes needed for lists keeps main-table rows and pages small. Narrowing IDs to a constant-sized result set first and consulting the main tables only afterward is important not only for computational complexity but also for cache efficiency. Frequent large Sequential Scans can also evict other hot pages from cache.

Once the working set no longer fits in memory and the OS cache, performance depends strongly on the random-I/O capability of the storage. HDD random I/O is generally only on the order of hundreds of IOPS, while SSDs and NVMe devices can be orders of magnitude faster, but the exact figure varies greatly with product, RAID configuration, cloud settings, and concurrency. The QPS achievable at a scale of millions of posts cannot be stated confidently without measuring the current schema on storage similar to production. Cache-saturation estimates can be calculated from capacity, but the actual scalability limit must be determined by benchmark testing.
## Aside

Storing snippets in the database means that the backend holds presentation knowledge about “how this will be displayed,” which feels awkward from the standpoint of separation of responsibilities. A snippet that is functionally dependent on the body is also a violation of third normal form. It is also unpleasant that changing the snippet format or character limit requires rewriting database records. Nevertheless, this is one of those cases where the discomfort has to be accepted for practical reasons.

Separating the bodies of posts and user profiles is a form of vertical partitioning. It can also be viewed as splitting the management of data according to the characteristics of its attributes. The body data alone could be placed on a different database server, stored in a column-oriented database, or put in S3 and fetched directly by clients. Bodies of old articles could be compressed and moved to archival storage. Tables such as post_likes and user_follows could also be managed on separate servers.

Given the above, retrieving a list of resources should always be thought of as a two-stage process: first generate the list of IDs matching the condition, then collect attributes associated with those IDs. With a single RDB server the two stages can be performed in one query, but it can still be a good idea to write them deliberately as two stages with a subquery. The following two queries are equivalent, and the latter may be slightly slower, but writing it in the latter form is less error-prone if the data is vertically partitioned later.

```sql:small
SELECT id, nickname, snippet
FROM users WHERE id > 0x0000000000020001
ORDER BY id LIMIT 10;

WITH cand_ids AS (
  SELECT id FROM users
  WHERE id > 0x0000000000020001
  ORDER BY id LIMIT 10
)
SELECT u.id, u.nickname, u.snippet
FROM users AS u
JOIN cand_ids AS c ON u.id = c.id
ORDER BY c.id;
```

The ``0x0000000000020001`` used here is 131073 in decimal. Hexadecimal integer literals with the ``0x`` prefix are available in PostgreSQL 16 and later. To run the same query on PostgreSQL 15 or earlier, write the decimal value 131073 instead.

PostgreSQL also has a mechanism called TOAST (The Oversized-Attribute Storage Technique), which can implicitly compress large variable-length values or move them to a separate storage area. An external TOAST value that is not part of the SELECT target is not necessarily read on every query. However, a TOAST pointer or inline portion remains in the main table, and short bodies may be stored inline. Wider rows reduce the number of records that fit on one page, so separating bodies into another table is still effective when the goal is to keep frequently listed posts and users small. Explicitly separating data with different access frequencies also makes it easier to avoid queries that accidentally fetch full bodies.

![TOAST illustration](/data/help-postgres-toast.png){grid,size=large}

Column storage can be tuned with ``PLAIN``, ``MAIN``, ``EXTERNAL``, and ``EXTENDED``, and the compression method can also be selected per column. These settings do not simply mean “always move short values to another area”; storage is decided according to row size and TOAST thresholds. TOAST's primary purpose is to keep heap rows within pages while supporting large variable-length values. This project configures LZ4 as the compression method to balance compression ratio and decompression speed. Even so, if hot list attributes and large bodies have clearly different access frequencies, splitting the tables expresses the design intent more directly.

If read queries become heavy, master-replica replication can provide relatively straightforward load distribution. Run two database servers and send update queries only to the primary; those updates are propagated automatically to the replica. Read queries can then be distributed across both servers, roughly halving the read load per server; adding more replicas can reduce it further. Promoting a replica when the primary fails also improves availability. This does not reduce write load, however. Replication lag also means a read from a replica may not reflect an immediately preceding update, so techniques are needed such as routing reads immediately after a write only to the primary, or placing the just-written state in a cache and injecting it into the UI.

If vertical partitioning and replication are still insufficient, horizontal partitioning is the next step. Partitioning by user ID is a straightforward approach. Assignment could be mechanical using a hash, but another direct design is to maintain a user_partitions table, or an equivalent KVS, that records the partition containing each user. To read users, first locate the partition by user ID and then access that database server; to read posts, locate the partition from the author's user ID and then access that server. Follow relationships can be duplicated on the databases of both the follower and the followed user. If vertical partitioning has already been introduced, JOIN-heavy queries should already be uncommon and the practice of obtaining an ID list first and then accessing another database should already be established. The final step is simply to make the destination partition depend on each ID. If a utility exists for moving a user's related data between partitions, operation need not be especially difficult.

At very large scale, an “All” view of the post list becomes nearly meaningless. Few people want to see every post from complete strangers. It would likely be replaced by something positioned as “Pickup” or “Topics”: maintain a small database containing only recent posts, compute high-quality items or items likely to match each user's interests in batch processing, and present those instead.

At large scale, “celebrity users” also become an operational concern. A user may be followed by tens of thousands of people, or a single post may receive likes and replies at an extraordinary rate. Optimizing reads alone does not solve a saturated write path. In that case, a dedicated data-management mechanism for celebrity users may be appropriate: serve post contents from cache, enqueue follows, likes, and replies for asynchronous processing, and omit notifications because they no longer have practical meaning. Sudden virality or controversy can happen even to ordinary users, so it may also be useful to switch all writes, or writes for a particular user, to asynchronous processing once load exceeds a threshold. This is temporal load distribution. Asynchronous updates are not immediately visible on screen, so the cache must compensate—for example, keep each user's pending updates in cache and adjust the display as though they had already been committed to the database.

There are many other ways to use a cache server. For example, caching the active-user list built inside listPostsByFollowees alone can drastically reduce database load. If the contents of each active user's latest 20 posts are cached as well, timeline rendering can often complete without accessing the database at all. Cache design is outside the database-design topic of this article, so it is not discussed further here, but it is important. A cache can disappear at any time, however, so the fundamental requirement is still a database design that works satisfactorily without it.

Despite all of the scalability discussion above, STGY's current goal is not to maximize scalability. It is to build a simple, conventional, textbook-like system that implements the fundamental functions of an SNS straightforwardly. Especially during the early stages of development, the schema should be easy to understand, develop, and maintain, and the current schema meets that goal. Premature optimization that causes development to stall before the service ever becomes popular would be pointless, so starting from a simple architecture is important.
